# Архітектурний контракт

Обов'язковий для всіх задач. Якщо задача вимагає відступити від нього — спершу змінюється цей файл окремим рішенням оркестратора.

## Пакети

| Пакет | Шлях | Що містить | Від кого залежить |
| --- | --- | --- | --- |
| `@shinobi/content` | `packages/content` | Схеми Zod і типи контенту, згенеровані дані, тексти `uk`, валідатор замкненості | — |
| `@shinobi/core` | `packages/core` | Стан гри, `advance`, `dispatch`, усі правила | типи й дані `content` передаються параметром |
| `@shinobi/sim` | `packages/sim` | Боти, звіти балансу, CLI | `core`, `content` |
| `@shinobi/web` | `apps/web` | Svelte 5 + Vite, IndexedDB, UI | `core`, `content` |

Пакети споживаються як вихідний TypeScript (`"exports": {".": "./src/index.ts"}`), без окремої збірки.

## Час і випадковість

- Час — цілі мілісекунди ігрового часу в `state.now`.
- `advance(state, ms, content)` іде подіями: шукає найближчу подію (кінець дії, касту, перезарядки, секундний тік ефектів, тік села, загоєння Рани) і стрибає до неї. Жодних циклів по фіксованих кроках.
- RNG — `sfc32` із сідом; стан потоків лежить у `state.rng` (`action`, `combat`, `loot`, `world`). Аналіз бою працює на клоні стану з власним сідом.
- У `core` заборонені `Date`, `Math.random`, `performance`, `window`, `document`, `setTimeout`.

## Стан

`GameState` — звичайний об'єкт, що серіалізується в JSON: без класів, `Map`, `Set`, функцій. Змінюється лише всередині `advance` і `dispatch`.

```ts
interface GameState {
  v: number;                       // версія формату збереження
  now: number;                     // ігровий час, мс
  rng: Record<string, [number, number, number, number]>;
  packs: { id: string; version: string }[];     // пакети, з якими зроблено стан, у порядку завантаження
  rankOrder: string[];                          // порядок рангів на момент запису (запасний шлях, якщо рангу бракує)
  dormant: Record<string, DormantPack>;         // дані пакетів, яких зараз немає
  player: { name: string; rank: string; natures: string[] };   // ранг і природи — id з контенту
  skills: Record<string, { xp: number }>;       // за навичками контенту
  mastery: Record<string, { xp: number }>;      // ключ — id майстерності
  pools: Record<string, { xp: number }>;
  bank: Record<string, number>;
  currencies: Record<string, number>;           // за валютами контенту (`ContentDb.currencies`)
  known: Record<string, true>;                  // відкриті техніки, рецепти тощо
  slots: ActionSlot[];                          // слоти дій; у слоті частка швидкості
  flags: Record<string, true | number>;
  // далі додають етапи: combat, loadouts, pouch, wounds, bingo, missions, world, village, quests, goal, stats
}
interface ActionSlot {
  action: { kind: string; id: string } | null;
  progress: number;   // цілі одиниці роботи: мс × share
  share: number;      // ціла вага в тисячних; 1000 — повна швидкість; сума активних слотів — 1000 (пул `K.clone.pool`, коли їх два)
  data: JsonValue;    // дані виду дії, серіалізуються
}
```

Кожен етап додає свої гілки стану й підвищує `v` із міграцією.

## Правила

Системи, види дій і постачальники модифікаторів зібрані в один явний упорядкований набір `defaultRules` у `rules.ts` — це правила пакета `core`. Глобальних реєстрів і реєстрації під час імпорту немає, крім одного винятку: `rules.ts` під час імпорту викликає `markCacheable(defaultRules.modifierProviders)` (позначає постачальників ядра, чиї підсумки можна тримати, див. «Підсумки під час `advance`»); без цього був би цикл імпортів. `advance`, `dispatch`, `deserialize`, `getMod`, `advanceOffline` приймають `rules` останнім параметром; тести й боти можуть передати власний набір.

**Правила з пакетів.** Гра з модами будує правила через `composeRules(base, packs, content)`: функція `rules` кожного пакета (`ContentPack.rules`, тип `PackRulesFn = (base, content) => Rules`) отримує вже зібрані правила й повертає розширені. Порядок — завантаження з `content.packs` (порядок масиву `packs` не важить, пакети поза `content` ігноруються). Пакет без `rules` нічого не змінює, тож `composeRules(defaultRules, [corePack], content)` — це `defaultRules`. Допоміжні функції не змінюють вхідний набір:
- `addRule(rules, 'systems' | 'modifierProviders', запис)` дописує в кінець; `addRule(rules, 'actionKinds', ключ, вид)` додає вид під вільним ключем (зайнятий ключ — помилка);
- `wrapRule(rules, 'actionKinds' | 'systems', ключ, обгортка)` замінює запис тим, що з нього робить `обгортка`; вид дії шукається за ключем, система — за `System.id` (системи ядра мають id `action`, `combat`, `wound`, `village`, `quest`); відсутній запис — помилка, тож обгортка не промахується мовчки;
- гачки бою й ШІ пакет змінює, розгортаючи `rules` у новий об'єкт.

Функція пакета мусить бути детермінованою: без годинника, `Math.random` і власного стану поза тим, що вона кладе в правила. Рушій цього не перевіряє. Тип `Rules` визначає ядро, тому функція типізується в ядрі, а не в `packages/content`; `testmod` бере її з `@shinobi/core/testmod` (застосунок цього входу не збирає). Хост (sim, а далі застосунок) будує гру через `composeGame(packs)`, що повертає `{ content, rules, failed }`: пакет не-`core`, який не складається (контент або `rules`), викидається разом із пакетами, що від нього залежать, і складання повторюється, тож `content` і `rules` завжди описують один набір пакетів. Помилки `rules` і `addRule` / `wrapRule` називають пакет.

**Захист рушія від пакетів.** Усе, що додав пакет не-`core` (системи, види дій, постачальники модифікаторів), `composeRules` позначає пакетом і огортає: система, чий `nextEventIn` повертає не `null` і не невід'ємне ціле, що кидає з `nextEventIn` / `elapse` / `run` або просить подію через +0 мс `STALL_LIMIT` разів поспіль, вимикається на сесію (не зберігається, після завантаження пробується знову), а UI отримує подію `ruleDisabled { pack, rule, reason }`; вид дії, що кидає, зупиняє дію слота з тією ж подією; постачальник, що кидає, нічого не додає. Правила `core` не огортаються: помилка в них лишається гучною.

Захист охоплює помилки, а не зловмисність. Усе, що повертає зворотний виклик пакета, перевіряється за формою: дерево вимог, інтервал (ціле від 1), результат завершення, записи модифікаторів (кінцеве число, для `mul` більше нуля, відома група) — неправильна форма вважається відмовою цього правила; `ruleDisabled` потрапляє і в підсумок офлайну (`rulesDisabled`). Система пакета має бюджет подій на ігрову годину (`K.engine.packEventsPerHour`; більше — вимкнення з причиною `budget`), лічильник кроків +0 мс веде кожна система окремо, а `state.now` належить `advance`: система, що його змінила, вимикається, а час повертається. Незалежно від джерела, час циклу дії не менший за `K.engine.minActionMs`, а підсумок модифікатора лежить між `K.engine.modMin` і `K.engine.modMax`. Власний `combatAi` пакета повертається до ШІ, який він замінив, коли кидає або дає не рішення (гачки бою захищає задача бою). Пакет, що навмисно псує стан напряму (видаляє `skills`, ставить `now` у NaN), поза цією гарантією: код пакета вважається таким, що не атакує стан.

Кожна помилка складання, викликана пакетом, — `PackError` з полем `pack`; `composeGame` читає це поле й ніколи не розбирає текст повідомлення.

Словники читаються з контенту, не з коду: навичка, яку тренує дія, — це перша навичка з потрібним `activity` (`drill`, `insight`, `course`, `patch`, `map`; навички `tech`, `recipe` і `station` мають власні списки), валюта з роллю `money` / `renown` / `study`, перший ранг без `academy` — випуск з Академії. Іспит рангу — команда `exam.start { rank }` (`exam.genin.start` лишається псевдонімом для першого рангу після Академії).

```ts
interface System { nextEventIn(state, content, rules): number | null; elapse?(state, dt, content, rules): void; run(state, content, rules): void }
interface ActionKind {
  has(id, content): boolean;
  requirements(state, id, content, rules): Req | null;   // перевіряється на старті й після кожного завершення
  intervalMs(state, id, content, rules): number;
  complete(state, id, content, rules): 'continue' | 'stop' | void;
  start?(state, slot, id, content, rules): void;
  stop?(state, slot, id, content, rules, reason): void;
  flow?(id, content): { makes: string[]; uses: string[]; speed: string } | null;   // що дія робить і що витрачає: для зв'язку слотів клона
  fullSpeed?: boolean;                                                            // дія не сповільнюється часткою слота (бій); охоронець (`guardKind`) переносить прапорець і для видів пакетів, і для обгорнутих (`wrapRule`)
}
```

Увесь облік часу й прогресу — цілими числами; жодних дробів у прогресі й у пошуку найближчої події.

### Слоти дій і клон

Додатковий слот відкриває знання техніки з полем даних `opensSlot` (тіньове клонування — слот 1, `technique-slots.json`); слот 0 є завжди. `clone.ts` (`cloneSlots`, `slotCount`, `isCloneSlot`, `growSlots`): слот додається, коли техніку вивчено (`readScroll`) або коли дію вперше запускають у слоті, якого ще немає; він ніколи не зникає, а слот, якого жодна відома техніка не відкриває, інтерфейс не пропонує (`isCloneSlot`). Слот — звичайний елемент `slots`; **клон — окреме тіло** `state.clones[слот]` (`CloneBody`), яке працює в цьому слоті. Перебудова клонів — рішення автора 18.11 (правки зрізу, розділ 5, рядок 19; версія збереження 20).

- **Швидкість.** Спільного пулу швидкості немає: `rebalanceShares` дає `SHARE_FULL` кожному слоту з дією (порожній слот — 0; слот 0, коли не працює ніхто, — повний). Персонаж і кожен клон працюють на повній швидкості; ціна клона — його чакра. `ActionKind.fullSpeed` більше нічого не робить; зв'язку слотів (`slotLinks`, `K.clone.link`) немає, `flow` лишився даними виду дії.
- **Тіло клона.** `CloneBody`: `life` (ціле, частки `LIFE_FULL` = 1e9; 0 розвіює клона), `max` (пул чакри при створенні — для смужки), `born`, `bag` (предмети: торба), `purse` (валюти, що клон здобув), `pouch` (власна торбинка для бою, наповнюється з `bag`), `xp` (досвід навичок, що клон здобув, — **уже з модифікаторами**), `mastery` (Майстерність: сума, навичка, частка пулу), `fight` (бій клона, якщо його дія веде бій), `doomed` (позначка смерті до кінця миті). `state.fatigue` — втома розуму в тисячних частках мс.
- **Виконавець і підміна.** Увесь код, що виконує дію слота (цикл, зупинка, `start`, крок бою, перевірка вимог для запуску), іде як `asPerformer(state, слот, fn)` (`performer.ts`): на час `fn` у `state.bank`, `state.currencies`, `state.pouch`, `state.combat` стоять торба, гаманець, торбинка й бій клона, а `actingPerformer()` каже, чия це дія. Підміна синхронна й повертається в `finally`; вкладені виклики (в тому числі для різних слотів) дозволені. Тож усе, що ядро читає як «Банк» і «бій», у дії клона читає його власне. `fightOf(state, слот)`, `allFights(state)` — бої виконавців. `GameState.combat` — бій персонажа (слот 0), бій клона — `clones[слот].fight`.
- **Життя за чакрою** (`clone-life.ts`, система `clone`). Створення (`clone.create { slot?, items? }`, `createClone`): чакра ділиться порівну (пул ÷ (`n` + 1), `chakraDivisor` читають `planningSnapshot`, `playerMaxChakra`, `followChakraPool`), клон бере з Банку `items` (типово — стеки торбинки персонажа: `defaultPouch`), з'являється там, де стоїть персонаж, і стоїть (дія `stand`). Дія в клонячому слоті без клона створює клона з торбою за замовчуванням (`startRefusal` перевіряє дію так, ніби цей клон уже є: `probeBody`). Швидкість витрати — `lifeRate`: цілі частки `LIFE_FULL` на мс = `LIFE_FULL` ÷ (`K.clone.life[вид дії]` або `default` секунд × подовження), подовження = (1 + `K.clone.lifeMastery` × рівень Майстерності техніки клонування − 1 + `K.clone.lifeSkillLevel` × рівень `K.clone.lifeSkill` (Медитація)) × (1 + модифікатор `clone.pool`). Стоїть — майже нічого, фізична праця — мало, техніки й бій — багато (дані). Система `clone` має подію «життя скінчилося» (`nextEventIn`), знімає життя в `elapse` і розвіює клона в `run` (після бойової системи тієї ж миті). Клон, чия дія закінчилася (завершення, нестача, зупинка рукою), стоїть; зупинка стоячого клона розвіює його (`action.stop`); `clone.dispel` розвіює будь-якого.
- **Знання після розсіювання.** У дії клона `gainXp` і `grantMastery` (`progression.ts`) складають результат (модифікатори вже застосовано, разом із бонусом місця, де клон стоїть) у `body.xp` / `body.mastery`; `dispelClone` передає їх персонажеві (`takeXp`, `takeMastery`: рівні, події, розблокування), а торбу, торбинку й гаманець — у Банк. Те саме при розсіюванні від вичерпаної чакри (`life`) і від смерті (`death`). Подія `cloneDispelled { slot, cause, xp, fatigueMs }`. Досвід і Майстерність бою клона лишаються в `CombatState.pending` до виграшу (як раніше): виграш і зупинка слота виплачують їх у тіло клона, програш скидає (`dropPending`).
- **Один виконавець — одна дія** більше не діє: та сама дія йде в кількох виконавцях. `ActionKind.unique(id, content)` лишає правило (`error.sameActionElsewhere`) там, де дія єдина за природою: бій з набігом села (`fightKind`: один бій на набіг), місія (її власне `error.missionRunning`), розвідка гекса (`exploreKind`), іспит `senseiTest`. Авторозвідка, подорож, збір, варіння й решта можуть іти в кількох виконавцях одночасно.
- **Втома розуму.** `fatigueFor` — година роботи, що стоїть за прийнятим досвідом (досвід ÷ `rate(рівень навички)`), навичка за навичкою, × `K.clone.fatigue.share`, не довше `maxMs`; додається до `state.fatigue` при розсіюванні. Поки вона триває: `clone.create` і дія в клонячому слоті без клона відмовляють (`error.cloneFatigued`); `fatigueProvider` знижує швидкість усіх навичок персонажа (слот 0) на `K.clone.fatigue.slow` (запис `mod.source.fatigue`; клонів не чіпає). Знімається за `fatigueRate`: 1 мс за мс, швидше на `decayPerLevel` за рівень Медитації й ще на `meditating`, поки персонаж сам виконує дію, що тренує цю навичку. Система `clone` будить гру, коли втома скінчиться.
- **Бої.** Кожен виконавець має свій бій: `combatSystem` бере `allFights(state)` і кожен бій веде як свого виконавця (`asPerformer`): годинник бою тече на повній швидкості, бій клона користується його торбинкою й торбою, здобич клона лягає в його торбу. Відмов `error.fightBusy` немає. Пул чакри кожного бою слідує за дільником (`followChakraPool` на початку кроку бою кожного виконавця). **Смерть клона** (поразка в бою, у тому числі в бойовому етапі місії): Ран гравцеві немає, лічильники поразок гравця й Книги Бінго не чіпаються, подія `playerDefeated { clone: true }`, `TargetReport.cloneLosses`; клон розсіюється без повторної спроби (`doomed`, система `clone`), знання повертаються, крім досвіду програного бою; новий клон з'являється там, де стоїть персонаж. Прогноз бою (`analysis.ts`) працює на копії стану: клони лишаються (вони ділять пул), їхні бої й втома скинуті.
- **Збереження (версія 20).** Нові гілки: `clones` і `fatigue` (`dormant-places`: `clones: 'dropped'`, `fatigue: 'none'`). Міграція 19 → 20 дає кожному клонячому слотові з дією клона з повною чакрою, порожньою торбою й слотами торбинки персонажа; бій, що належав клонові (`combat.owner > 0`), переходить у `clones[слот].fight`; у `combat` лишається бій персонажа. Завантаження чистить тіла (слот мусить існувати, предмети, навички й ключі Майстерності — з контенту, числа обмежені), слот без клона втрачає дію, фігура слота без клона зникає. Бій клона відновлюється разом з боями інших виконавців (потрібні слот і дія).
- **Місця сили.** `pointsProvider` і тренувальні точки клітинок (`worldProvider`) дають бонус лише тому виконавцеві, що стоїть на них, і лише його діям (читають `actingPerformer()`): бонус не діє на чужі дії, клон, що лише стоїть на місці, не дає його нікому.
- **Телеметрія.** Лічильники `clone.openMs` (відколи відомо техніку з відкритим слотом), `clone.runMs` (поки існував хоч один клон), `clone.pair.<вид=id>|<вид=id>` (цілі мс) і селектор `cloneTelemetry(state)`.

## Команди й події

- UI та боти змінюють гру лише через `dispatch(state, command, content)`. Команда — об'єкт `{ type: 'action.start', ... }`. Результат — `{ ok: true }` або `{ ok: false, reason: <ключ локалізації> }`.
- Ядро повідомляє про разові події через `state.events` (рівень, Майстерність, предмет, крок доручення, рядок журналу бою). Черга не зберігається; UI її вичитує й очищає.

## Вимоги

Одне дерево умов для відкриття технік, чеклістів, етапів місій, цілей доручень і закріпленої мети:

```ts
type Req =
  | { t: 'skill'; skill: SkillId; level: number }
  | { t: 'technique'; id: string } | { t: 'rank'; rank: Rank } | { t: 'nature'; nature: NatureId }
  | { t: 'item'; id: string; n: number } | { t: 'quest'; id: string; step?: number }
  | { t: 'building'; id: string; level: number } | { t: 'flag'; id: string; n?: number }
  | { t: 'currency'; role: string; n: number }   // баланс валюти з цією роллю (`renown` — Репутація, `study` — Intel)
  | { t: 'all'; of: Req[] } | { t: 'any'; of: Req[] };
```

**Доручення й іспити.** Ціль кроку доручення — `req` (дерево вимог), `counter` (лічильник виріс на `n` від початку кроку; `also` додає до нього інші лічильники) або `pay` (гравець заплатив `n` валюти з роллю `role` командою `quest.pay { quest }`; крок `pay` Intel — «Вислідити»). Крок може мати `opens` — прапорці, що піднімаються, щойно крок стає активним (зона боса, операція, регіон, які він просить); рушій піднімає їх і для ланцюжка, збереженого до появи кроку. Нагорода ланцюжка може закріпити мету (`goal`). Іспит із полем `then` складається у два заходи: чекліст відкриває письмовий тест (він швидшає від навичок `reduceBy` і Intel), тест піднімає прапорець `exam.<id>.written`, а коли виконано `then`, та сама команда `exam.start` вручає ранг; без `then` ранг дає сам тест. Іспит із `finale: true` завершає історію пакета: після нього інтерфейс показує фінальний екран замість діалогу підвищення. Інтерфейс бере випробування другого заходу з операцій, чий `unlock` відкривають кроки ланцюжка з `then`.

`evalReq(state, req, content)` повертає дерево з полями `met`, `current`, `target`, `ref` (на що посилається рядок) і `children`.

## Модифікатори

Будь-який бонус — запис `{ key, op: 'add' | 'mul', value, group: 'character' | 'village' | 'items', source: EntityRef | string }`. Ключі — рядки виду `xp.skill.tai`, `xp.all`, `interval.skill.herb`, `cost.chakra`, `mission.duration`. У межах групи значення додаються, групи перемножуються. `getMod(state, key, content)` повертає підсумок і список складників — UI показує його на кожному відсотку.

**Підсумки під час `advance`.** Довге офлайн-вікно питає ті самі підсумки (`totalsOf`, `bonusOf`, `cycleFactor`, а також `lifeRate` клона через `keptValue`) сотні тисяч разів: на кожну подію кожного виконавця. Тому, поки йде `advance`, підсумки тримаються (`withKeptTotals` у `modifiers.ts`) доти, доки не зміниться те, що читають постачальники. Про зміну кажуть `touchMods(state)` — його викликають `emit` (усі події, крім `combatLog`), `dispatch`, початок `advance`, `rebalanceShares`, `placeAt`/`removeFigure`/`touchWorld`, створення й розвіювання клона, витрата тоніка, кінець втоми, добудова будівлі, шкода від набігу. Підсумки різняться за виконавцем (`actingPerformer()`). Тримаються лише для набору правил, де всі постачальники з ядра (`markCacheable`) і **жодне правило не від пакета**: система, вид дії, хук гексу чи хук бою пакета може написати те, що читає постачальник ядра, без `touchMods`, тож один такий запис вимикає тримання для всієї гри (гра з модом повільніша, але не хибна; ядро без модів лишається швидким). Постачальник пакета чи тесту може читати що завгодно, тож і він вимикає тримання. Підсумки тримаються лише для тих `rules`, з якими йде `advance`; виклик з іншими питає наново. Масив підсумків заморожений. Поза `advance` нічого не тримається — виклик, який змінив стан вручну, читає свіжі числа. **Новий постачальник ядра, що читає нове поле стану, мусить мати `touchMods` там, де це поле змінюється**; `VERIFY_MODS=1 pnpm test` перераховує кожен триманий підсумок і падає на розбіжності.

## Сутності й посилання

- Ідентифікатори контенту — `core:<slug>`; навички мають короткі id (`tai`, `katon`).
- `EntityRef = { kind, id }`, де `kind` — `skill`, `technique`, `item`, `recipe`, `mission`, `enemy`, `region`, `building`, `quest`, `gear`, `seal`.
- Маршрути UI — хеш: `#/skill/tai`, `#/technique/core:great_fireball`, `#/item/core:mint` тощо.
- **Правило посилань:** де б у UI не стояла назва сутності — у вимогах, рецептах, етапах місій, таблицях луту, підказках, журналі — вона є компонентом `EntityLink` і веде на сторінку цієї сутності. Голий текст із назвою сутності — помилка рев'ю.
- Кожна сутність контенту має назву й опис (`name`, `desc` — ключі локалізації). Валідатор не пропускає сутність без опису.
- **Правило відкриття.** Адреса `#/<вид>/<id>`, посилання й списки не мають розкривати те, чого гравець ще не знає. Скільки видно сутність, вирішує одна функція ядра `revealOf(state, ref, content, rules)`: `full` — усе; `name` — назва, значок і те, що відкриває сутність (вимога, що її показує й дошка; місія за назвою показує те, що її картка на дошці, ціль за назвою лишає дерево умов), без опису й без вмісту (вороги, нагороди й предмети в ній теж за правилом); `hidden` — нічого. `revealHint` дає ключ підказки, як дізнатися більше («Зустрінь у бою», «Розвідай клітинку»). Правило — дані `{ name?: терміни, full: терміни }` (терміни — «будь-який»; порожній список не виконується). Сильніше за все — поле `reveal` сутності; далі `manifest.reveal[вид]` пакета; далі `entityKinds[].reveal` виду; без правила сутність завжди `full`. Словник термінів закритий, це код рушія (`REVEAL_TERMS`): `always`, `known` (`state.known`), `owned` (є в банку чи рівень спорядження), `seen` (id у `state.shown`), `named` (її називає сутність, що сама `full` за власними термінами: відкрита зона, рядок крамниці, дошка доручень, досягнутий крок доручення, сторінка навички з її діями), `encountered` (ворог чи бос зустрінутий: рівень Бінґо від 1), `explored` (клітинка, регіон з такою клітинкою, знайдена точка), `adjacent` (регіон, де стоїть гравець, або поруч із розвіданим), `parent` (регіон клітинки чи клітинка точки видно за назвою), `actionable` (регіон відкритий: туди можна піти), `questStarted`, `unlocked` (власні `unlockReq`/`unlock`/`req`, а для операції ще її `unlock`), `{ req }` (довільне дерево вимог). Валідатор замкненості перевіряє, що термін пасує до виду (`encountered` — лише для ворогів і босів тощо) і що дерева вимог замкнені.
- **Станом правила є `state.shown`** (межа — кількість сутностей контенту, місце в таблиці `PLACES`). Ключ — `<id>@<вид>` (ідентифікатор спільний для двох видів — печатка й ворог — дає два записи). Пишуть його лише через одну функцію `addShown` (`shown.ts`, вона ж тримає межу): команда `reveal.mark { refs }`, яку інтерфейс надсилає, коли показав щось законно (рядок крамниці, рецепт у списку навички, винагорода місії, рядок вимоги): ядро приймає ref, лише якщо його вже видно хоч за назвою іншим правилом (тобто його називає відкрита сутність), інакше відмовляє всій команді (`error.revealRefused`); не більше 64 ref за виклик; повторна позначка нічого не змінює. Сторінка самої сутності позначити її не може; крім команди, запис робить банк, коли предмет надходить (щоб «тримав у руках» пережило останню одиницю). Міграція збереження засіває набір із того, що старе збереження доводить: банк, сумка, спорядження, звіти боїв, майстерність, відомі рецепти, Бінґо-книга.
- **Інтерфейс.** `EntityLink` малює за `revealOf`: `full` і `name` — звичайне посилання, `hidden` — «???» без посилання й id у DOM, з підказкою в `title`. `entityName` повертає «???» для прихованого, `entityDesc` — лише для `full`. `PageHost` перед будь-якою сторінкою (і обгорткою пакета) показує стан «Ще не відкрито» для `hidden`, а для `name` — назву з підказкою, якщо сторінка не оголосила `reveal: 'self'` (карта й сторінка місії самі ховають опис і вміст; для будь-якого id, якого немає в контенті, показується та сама сторінка, що й для прихованого). Прихований id не потрапляє в жоден атрибут DOM: тест `no-raw-entity-attrs` вимагає, щоб атрибут елемента, зібраний з id сутності, йшов через `entityAttr`/`idAttr`, а виняток мав записану причину. Рядок вимоги про приховану сутність лишається («???» і підказка), але без id. Пакети читають правило через `api.core.revealOf` і друкують назви через `api.link(ref)`; кроки доручень, до яких ланцюжок не дійшов, друкуються як «???».

## Пакети контенту й моди

Гра має лишатися відкритою для сторонніх модів і DLC. Це обмежує кожну задачу вже зараз, хоча завантаження модів гравцем — після MVP.

- **Увесь контент постачається пакетами.** Вбудований контент — пакет `core`; DLC й моди — такі самі пакети з власним простором імен (`dlc1:…`, `<mod>:…`). Ядро не має привілейованого шляху: воно реєструється так само, як реєструватиметься мод.
- **Пакет** — це маніфест `{ id, version, dependsOn, loadAfter }`, дані за тими самими схемами Zod, локалі, а пізніше й скрипти.
- **Збирання.** `composeContent(packs)` будує `ContentDb` у порядку залежностей. Пакет додає сутності у своєму просторі імен, а чужі змінює лише явними патчами; мовчазний перезапис і конфлікт ідентифікаторів — помилка з назвою пакета.
- **Жодних закритих переліків.** Ядро й UI не знають конкретних ідентифікаторів і не мають вшитих списків навичок, природ, рис, станів, видів дій, рангів місій чи типів точок інтересу: усе береться з `ContentDb`. Типи ідентифікаторів — відкриті рядки, які перевіряє реєстр, а не об'єднання літералів.
- **Особлива поведінка — через дані або `rules`.** Якщо сутність поводиться не як інші, це описано в її даних або підключено через `rules` (системи, види дій, гачки бою, постачальники модифікаторів, ШІ). Скриптові моди отримають той самий інтерфейс, тому глобальних реєстрів і прихованих особливих випадків у коді немає.
- **Збереження.** Стан зберігає список пакетів із версіями. Збереження завантажується й без пакета: його сутності відкидаються без помилки, решта гри працює; дані пакета лежать у кошику `dormant` і повертаються, коли пакет з'являється знову (розділ «Збереження»).
- **Перевірка.** У тестах є пакет `testmod`, що додає по одній сутності кожного виду. Гра з ним працює, а збереження, зроблене з ним, завантажується без нього.

### Форма пакета

Код — `packages/content/src` (`pack.ts`, `compose.ts`, `closure.ts`). Вбудований пакет — `packs/core/`, тестовий — `packs/testmod/` (його можна імпортувати лише як `@shinobi/content/testmod`, застосунок його не збирає).

```
ContentPack = {
  manifest: { id, version, dependsOn: string[], loadAfter: string[] },
  data:     сутності за списками ContentDb (кожен список необов'язковий),
  balance:  фрагмент { K, pace, capHours, milestones } — лише листки, які задає пакет,
  locales:  { uk, en? } — ключі <вид>.<id>.<поле>,
  icons:    { <вид>: { <id>: назва іконки } },
  patches:  Patch[],
  modifierKeys?: ключі модифікаторів, які оголошує пакет,
  rules?:   (базові правила) → розширені правила — типізовано, виконує задача ядра,
  ui?:      id UI-пакета в apps/web — лише оголошено,
}
```

- **Пакет — звичайні дані**, зібрані зі статичних імпортів під час збірки. Накладки (`overlay.ts`) застосовує код побудови пакета, а `composeContent` отримує вже готові сутності.
- **Простір імен.** Ідентифікатор — `<пакет>:<слаг>`. Лише `core` володіє ще й голими ідентифікаторами (`tai`, `katon`, `student`, `E`, `ryo`, …). Усі ідентифікатори іншого пакета починаються з `<id пакета>:`; `composeContent` це перевіряє.
- **Порядок.** Топологічний за `dependsOn` і `loadAfter`, за рівних умов — за id пакета; порядок вхідного масиву на результат не впливає. `ContentDb.packs` — маніфести в порядку завантаження.
- **Баланс.** Фрагменти зливаються вглиб; два пакети, що задають один листок, — помилка. Новий ключ чужого запису (`K.role`, `K.bossFx`, `pace`, …) мусить мати префікс `<пакет>:`. Числа лише одного пакета — у `K.ext.<id пакета>`.
- **Патч.** `{ target: { kind, id }, set?: {поле: значення}, append?: {поле: [елементи]} }`, де `kind` — назва списку (`enemies`, `items`, …). Виконується після злиття в порядку завантаження. `set` замінює поле, і два пакети не можуть задати одне поле — помилка; `append` додає елементи до списку, і кілька пакетів можуть дописувати в той самий список (за порядком завантаження). Патч до відсутньої сутності чи невідомого списку, а також `append` до не-списку — помилка з id пакета. Патч балансу `{ balance: { path: "K.power.E", set: число } }` замінює наявний листок (не об'єкт); два пакети не можуть задати один шлях, а відсутній шлях — помилка. Якщо патч робить сутність недійсною, винен пакет, що її змінив. Інакше чужу сутність змінити не можна: однаковий id у двох пакетів — помилка.
- **Замкненість.** Після збирання `validateClosure` перевіряє кожне посилання на словник і сутність, наявність чисел балансу для кожного члена словника (`K.power[ранг]`, `K.role[роль]`, `K.ryoPerMin[ранг місії]`, `K.dropChance/sell[трофей]`, `K.combo[комбо]`, `K.techFx/bossFx/itemFx[fx]`, `K.partDrop[ключ]`, `K.rep[стадія села]`, …), кожен ключ модифікатора будь-де в сутностях (модифікатори, `gear.fx.key`, `mission.resourceMod`) і природу модифікатора, що іконка названа сутністю свого виду (для пакетів не `core`), що `playerRanks[i].tier === i` і що рівні ШІ не вищі за найвищий ранг, наявність `name`/`desc` у локалі. `K.repPerMission` і `K.missionRateCap` для рангу місії необов'язкові: без запису репутація й межа ставки дорівнюють нулю (так у рангу `OP`; `V` має обидва); `K.ryoPerMin` обов'язковий. Помилка називає пакет, сутність і поле.
- **Конверт пакета.** Перш ніж читати пакет, `composeContent` перевіряє його форму (`manifest`, `data`, `balance`, `locales`, `icons`, `patches`, `modifierKeys?`, `rules?`, `ui?`; зайві поля — помилка); пакет із нечитним id називається за позицією (`#2`). Id пакета — `[a-z][a-z0-9_]*`, але не назва члена `Object` (`constructor`, `prototype`). Резерв `core` за самим вбудованим об'єктом пакета не робиться: тести збирають змінені копії `corePack`.
- **Дані пакета недовірені.** Усі накопичувачі за рядками з пакета — `Map`; ключі `__proto__`, `constructor`, `prototype` відхиляються будь-де в даних пакета (ідентифікатори, ключі записів, цілі патчів, ключі локалей, балансу й іконок) помилкою з id пакета.
- **Локалі.** Пакет не `core` додає лише ключі своїх сутностей (`<вид>.<пакет>:<слаг>…`) і вільні рядки під `x.<пакет>.`; `ui.*` та ключі інших пакетів відхиляються.
- **Ключі модифікаторів** не мають глобального реєстру: `ContentDb.modifierKeys` = сімейства ключів кожної складеної навички (`xp.skill.<id>`, …; для навичок з `activity: 'tech'` ще й вартість, час касту й відкат) + ключі, які оголосили пакети (для не-`core` — з префіксом `<пакет>:`).

**Відкриті словники** — списки сутностей у `ContentDb`, кожен член належить своєму пакету: `skills` (`activity`, `group`), `skillGroups`, `natures` (`strongAgainst` — колесо, `color` — назва CSS-токена, `opens` — ключові клітинки, `ayaNature`), `playerRanks` (порядок, `tier` і `academy` — ранг до випуску: без села, підсумку й випробування природи; `after` — id рангу, за яким іде цей: ранг стає одразу за ним, рівні за `after` йдуть за порядком завантаження пакетів, `tier` — позиція в підсумковому списку, а цикл `after` — помилка з назвою пакета), `techRanks`, `missionRanks`, `villageStages`, `traits` (`answer`), `statuses`, `states`, `combos`, `tags`, `roles`, `attackStyles`, `fightRegions`, `cellKeys` (запис «id → вимога»), `itemKinds`, `currencies` (`role`: `money`, `renown`, `study`; ціна запису магазину — `shop[].currency`, нагорода квесту — `rewards.currencies`, без валюти це `money`), `entityKinds`, `trophies`, `gearFx`, ідентифікатори рівнів ШІ (`ai.tiers`), а також стадії села (`villageStages` — ключ `K.rep`, що задає потрібну репутацію).

**Ранги Репутації** — список `renownRanks` (`renown` — поріг Репутації, `rewards`: `items`, `scroll` — сувій Бібліотеки до рівня `library`, `flags`, `mods`, `opens` — посилання для сторінки рангу). Ранг досягається один раз, коли баланс валюти з роллю `renown` не менший за поріг (`updateRenownRanks` у `renown.ts`, викликається з `updateQuests`, тож і після офлайну), тримається прапором `renownRank.<id>`, подає подію `renownRank`; модифікатори досягнутих рангів дає `renownProvider`. Назва, текст і рядок нагороди — ключі `renownRank.<id>.name`, `.desc`, `.reward`.

**Закриті (рушійні) переліки**, які мод не розширює даними, бо це код: види вузлів вимог (`Req.t`), види етапів місії й виплат, види ефектів технік і предметів, види точок інтересу (`poiSchema`), оператори й групи модифікаторів, правила ШІ (`AI_RULE_IDS`), а також дрібні перелічення з кількома значеннями (`seal.kind`, `mentor`, `extraSources`, ролі й обов'язки будівель, види ресурсів).

**Типи.** Типи `@shinobi/content` правдиві: ідентифікатори — `string`, записи за членами словників — `Record<string, T>` (тож `noUncheckedIndexedAccess` змушує перевіряти). Усі пакети й вебзастосунок перевіряються проти них; старого вузького відображення (`tsconfig.legacy-ids.json`) і воріт `typecheck:open` більше немає.

`constants.ts` віддає колишні переліки (`SKILL_IDS`, `NATURE_IDS`, …), виведені з даних пакета `core`, із позначкою `@deprecated`; вони зникнуть, коли ядро й UI читатимуть словники з `ContentDb`. `iconFor(kind, id, icons)` читає передану таблицю (`content.icons` містить іконки всіх пакетів); `MODIFIER_KEYS` — застарілий експорт, похідний від `content.modifierKeys`.

### Бій у пакеті: статус, комбо, риса, природа, особливість боса

Рушій бою (`packages/core/src/combat`) не називає жодного ідентифікатора статусу, комбо, риси, природи, тегу, ролі, навички чи особливості: тест `combat-packs-literals.test.ts` читає ідентифікатори з даних `core` і падає, якщо знаходить їх у коді як рядок (виняток — перелік у самому тесті з поясненням). Усе, що пакет додає, працює без правок рушія:

- **Статус** (`statuses`). Дані: `state` (стан техніки, що його накладає), `effects` (зміна характеристики `modifier` і/або шкода за секунду `periodic` — частка удару `hit` або максимального здоров'я `maxHp`), `duration` (секунди або `{ byRank }` — рядок `K` за рангом техніки), `stacks` (скільки шарів), `refresh` (`replace`, `longest`, `strongest`), `suppresses` (риса чи ефект, що вимикається), `interrupts`, `tally` (назва в звіті). Числа — шляхи в `K` (`"wet.slow"`, `{ path, oneMinus }`, для пакета `ext.<пакет>.<ключ>`). Один статус — один або кілька ефектів (`<id>`, `<id>#1`, …); очищення знімає всі.
- **Тег** (`tags`). `onHit` — що робить удар техніки з тегом (`status`, власний ефект `effect`, `cancelCast`), `onUse` — що робить знаряддя з сумки, `removes` — які ефекти знімає з гравця після касту, `hitsAll`, `guard`, `pouch` (`sweep`, `snare`, `venom` — як діє знаряддя в сумці). Роль (`roles`) може мати `hitsAll`.
- **Комбо** (`combos`). `nature` (навичка техніки) або `tag`, `onState` (стан цілі до удару) і `effect.kind`: `boost` (підсилює шкоду за секунду), `lengthen` (подовжує статус самої техніки), `status` (накладає `effect.status` зі значенням `K.combo[id]`), `burst` (знімає стан і б'є на `K.combo[id]` удару). Число — `K.combo[id]`; техніка може мати `guaranteedCombo`.
- **Риса** (`traits`). `answer` — тег, що її відповідає (авто-екіпіровка, сумка, ШІ й аналіз бою беруть відповіді з даних: техніка відповідає тегом або станом, що вимикає рису; знаряддя — тегом), `mods` (множники характеристик, вимикаються, коли щось `suppresses` рису), `regen`, `swarm` (рядок `K` для зграї), `inflicts` (ефекти, які риса накладає на гравця), `casts`, `priority` (порядок відповіді ШІ), `hook` — гачок, якщо даних не досить.
- **Природа** (`natures`). `strongAgainst` — колесо; сила — `K.wheel`. Чужу природу пакет змінює патчем `append` до `strongAgainst`. Навичка-природа має той самий id, що й природа.
- **Особливість боса** (`bosses[].special`). `kind`, `fx` (рядок `K.bossFx`), `hook`, а склад бою — з даних: `companions`, `bodies`, `fleeAt`, `nature`, `adds`. Поведінку, яку дані не виражають, реалізує **гачок** (`FightHook`), який пакет додає у `fightHooks` своєю функцією `rules`; ім'я гачка — у даних. Гачки читають числа один одного лише як ключі `c.data` (наприклад `caster.everyMs`), а не через ідентифікатори інших гачків.

Вбудовані гачки `core` (риси Caster, Evasive, Illusionist, Hidden, Poisoner і особливості босів) лежать у `packages/core/src/corepack` і підключаються в `defaultRules` так само, як підключатиметься мод; у `combat` лишилися лише гачки рушія (мовчазне заперечення удару й підтримка команди). Збережений бій несе ефекти, риси й тег-ефекти за ідентифікаторами: невідомі пакету (інший пакет не завантажено) риса, природа, комбо чи ефект при завантаженні відкидаються без помилки, а бій проти невідомого запису скасовується.

**Фаза `publish` гачка.** Гачок може мати `publish(ctx, c)`: він обчислює з даних числа для свого тіла й записує їх у `c.data` для інших гачків (спеціальність боса підсилює рису саме так: `caster.everyMs`, `evasive.rampTo`, `illusionist.everyMs`). `publish` кожного гачка тіла виконується до будь-якого `init` щоразу, коли тіло вперше читається, — і для свіжого, і для завантаженого зі збереження. Тому порядок реєстрації гачків не важить, а бій зі старого збереження отримує ті самі числа, що й новий. Запис ідемпотентний: ключ пишеться, лише якщо його немає.

**Огородження гачків пакета.** Кожен виклик гачка проходить через одну межу (`combat/fight-guard.ts`), яка не знає фаз бою й тому переживе перебудову циклу. Гачок `core` і рушія (без запису походження в `originOf`) виконується як є й падає голосно. Гачок іншого пакета (його записує `composeRules` через `tagOrigin`) не може зупинити, повісити чи зіпсувати бій помилкою: межа ловить виняток, перевіряє значення, що гачок повертає (`stat` і множники — скінченні від 0 до `K.combat.hookStatMax`; `castInfo` — задокументований об'єкт; `working` і `leader` — булеві), перевіряє форму того, що гачок лишив у `timers`, `data` і `effects` тіла (таймер — об'єкт із цілим розміром не меншим за `K.combat.timerMinMs`; числа скінченні; ефект правильної форми), перевіряє змінений план атаки й рахує події гачка за секунду бою (`K.combat.hookEventsPerSec`; `K.combat.timerFires` — найбільше спрацювань одного таймера за мить). Будь-яка помилка завершає бій як `void` (без перемоги, поразки, здобичі й Рани), записує в `fight.fault` пакет, гачок і причину, вимикає саме цей запис гачка (не за id: помилка пакета не вимикає гачок `core` з тим самим id) до наступного завантаження, а `advance` видає `ruleDisabled` з `rule: fightHook.<id>`; гра продовжується новим боєм. Таймер приписується гачку, що його завів. Пакет не може зареєструвати гачок під id, який вже має інший запис. Збережений бій із зіпсованим таймером чи числом розбір відхиляє. Аналіз бою працює з відокремленою копією правил: його збої не вимикають гачок у живій грі й не дають подій, а число перерваних боїв повертається як `voided` (прогноз тоді ненадійний). Форму всього, що повертає функція `rules` пакета (системи, види дій, постачальники, гачки, ШІ), `composeRules` перевіряє й повертає `PackRulesError` з назвою пакета; `validateHooks` перевіряє, що кожен гачок, названий у даних, зареєстровано.

### Цикл бою: вичікування й дія

Час бійця складається з двох речей: **вичікує момент** (`wait`) і **дія** (`act`); єдина інша пауза — `rest` («переводить подих»). Фази відновлення, `idle` і окремого таймера звичайного удару немає. Усі бійці — гравець і вороги — живуть тим самим циклом `wait → act → wait`; стан (`Combatant`) несе `phase`, `act` (`{ kind: technique | basic | item | attack | rest, id, target }`), `phaseAt` (час початку фази), `timer` (кінець фази), `last` (остання дія: `kind`, `id`, `outcome` — `hit`/`miss`/`interrupted`/`none`, `damage`, `statuses`, `combos`, `at`), `waitMs` і `strikeMs`. Оглушення чи сковування не є фазою: вони лише зупиняють `timer` (швидкість 0).

- **Вичікування.** Тривалість — `waitMs` тіру ШІ (`content.ai.tiers[].waitMs`; вищий тір вичікує менше). Гравця веде тір його рангу (`aiTierOf`), ворога — тір, названий у даних ворога (`aiTier`, необов'язкове), інакше найвищий тір, чий мінімальний бойовий рівень (`K.ai.enemyTier`) досягнуто. Пакет додає тір зі своїм числом. Наприкінці вичікування ШІ гравця (одна функція `combatAi`) обирає дію; вичікування і є його «реакцією», окремої затримки реакції немає.
- **Дія гравця.** Техніка триває її `cast` і діє наприкінці; кінець ставить перезарядку. Звичайний удар — окрема дія: коштує `K.basicCost` витривалості, триває `K.basicCast` і влучає наприкінці. Предмет сумки діє одразу, а дія триває `K.pillAction`. Коли не можна заплатити ні за жодну техніку, ні за звичайний удар, гравець `rest`: `K.rest.s` секунд, і від обох пулів повертається частка `K.rest.share`. Якщо удар не можна оплатити, а якась техніка лише чекає перезарядки, гравець вичікує ще раз.
- **Дія ворога.** Після вичікування починається видимий замах звичайної атаки (`strikeMs` = `K.eInterval` мінус вичікування тіру, тож частота атак не змінилась), наприкінці — удар. Гачки-таймери (замах Кастера, удари суперника) лишаються таймерами гачка.
- **Час касту.** `technique.cast` (секунди) — число самої техніки: `K.castByRank[ранг] × K.castByRole[роль]` або ручне значення в даних зрізу; від кількості печаток не залежить (печатки лишаються лише для показу). Майстерність скорочує його (`K.masteryCast`) до `K.castFloor`, чужа природа розтягує. Дія практики показує цикл як фокус + каст: `practiceSplit(state, id, content)`.
- **Переривання.** Власну дію (каст техніки, звичайний удар) обриває влучання технікою з тегом переривання (`cancelCasts`), удар ворога з `AttackPlan.interrupts` і оглушення: дія завершується без ефекту, перезарядка не починається, частка `K.combat.interruptLost` витраченого з пулу втрачається, решта повертається, боєць повертається у `wait`. Замах звичайної атаки ворога й уже застосований предмет не обриваються.
- **Вигляд бою для інтерфейсу** (`fightStatus(fight, content, rules)`, `combatantStatus`): для кожного бійця `phase` (`wait`, `act`, `rest`), `suspendedBy` (ефект чи гачок, що зупинив годинник фази), `action`, `startedMs`, `endsMs` (при поточній швидкості; `null`, поки зупинено) і `last` з `atMs`. Події журналу бою (`FightLogLine`, подія `combatLog`): `cast` — дія почалась, `resolve` — закінчилась з ефектом, `interrupted` — обірвана, `hit`, `miss`; `by` — id бійця.
- **Захист — один автоматичний кидок.** Кожне влучання техніки чи удару кидає один раз: точність нападника проти ухилення захисника (5–95%, `hitChance`). Реактивного шару немає: ШІ не стежить за кастами заради захисту, вдале ухилення нічого не коштує. Точність = внесок рівня навички + `K.rating.accTier` × тір нападника. Ухилення гравця = `K.evaBase` + `K.rating.evaTier` × тір + внески вивчених захисних технік + модифікатор `evasion` спорядження й бонусів; навички «Ухилення» немає. До ухилення гравця проти ворога додається `K.rating.knowledge` за рівень знань про нього в Бінґо-книзі (запис без рівня вважається повністю вивченим). Тір ворога — мінімальний тір його тіру ШІ.
- **Захисна техніка пасивна.** Техніка з `combat.passive: { fx }` (рядок `K.passiveFx`: `evasion` — внесок при дієвому рівні, рівному рівню нападника) додає до ухилення від моменту вивчення, не потребує слота, не потрапляє в набір, автонабір і збережені набори (завантаження звільняє слот), а в бою її немає в руці. Внески складаються; внесок росте з дієвим рівнем (розділ «Дієвий рівень захисної техніки» нижче). Розклад за джерелами — `evasionParts` / `playerEvasionParts` (`base`, `tier`, `technique` з id, `modifiers`) і `fightStatus(...).player.evasion`. Влучання, що минуло гравця, пише в `last.avoidedBy` нападника й у рядок журналу `miss` (`via`) техніку, яка «підмінилась»: вибір серед відомих за часткою внеску з потоку випадковості бою (для гравця без таких технік — порожньо).
- **Переривання — властивість удару.** ШІ має лише просту перевагу: якщо ворог якраз кастує те, що можна перебити, у момент рішення він бере техніку чи знаряддя з перериванням; на тривалість чужого касту він не розраховує.
- **Цикл практики** = фокус + каст: фокус `K.practiceFocus.base + perLevel × (рівень техніки − 1)` (`practiceFocusSeconds`), каст — `K.practiceCast` від каста техніки (частка, щоб підгонка темпу бою не ламала цикли практики); `practiceSplit` дає обидві частини. Досвід навички за цикл — дані техніки (`practiceXp`, темп рівня × цикл при Майстерності 1) і від Майстерності не залежить; Майстерність за секунду росте з рівнем Майстерності (`K.mastery`: `perSecond × (base + L)`), а цикл, дія з явними `cycle` і `xp` (вправа, трава, перешкода, рецепт, практика Медитації) — розділ 2 моделі балансу (`practice-rates.test.ts`, `action-pace.test.ts`).
- **Тіри ШІ.** `student` (мін. тір 0), `genin` (1), `chunin` (2): кожен має `waitMs`; тір ворога береться з його `aiTier` або з порогів `K.ai.enemyTier` за бойовим рівнем. Окремі числа точності й ухилення для ворога — `K.rating.enemyAccTier`, `enemyEvaTier`.
- **Підгонка.** Таблиці `docs/balance-evidence/` (`baseline-dev-3f559af-*`, `fit-after-*`, `fit-status.json`, `fit-table.md`, `boss-defence.md`); `pnpm --filter @shinobi/sim exec tsx scripts/fit-record.ts` перезаписує їх, `packages/sim/test/fit.test.ts` тримає: таблиця не змінюється непомітно, а виконана ціль лишається виконаною. Інструменти пошуку чисел — `docs/balance-evidence/tools/`.
- **Огородження гачків.** Цикл не додає нових викликів гачків: вони йдуть тими самими місцями (`onAttack`, `onAttackHit`, таймери, `stat`, `onCancel` тощо) крізь `fight-guard.ts`, що фаз не знає. Нове, що гачок може повернути чи озброїти — `plan.interrupts` у `onAttack` — перевіряється там само (`after` бере лише булеве значення).
- **Союзники в бою.** Бік гравця — персонаж (`fight.player`) і, коли є, союзники (`fight.allies`, необов'язкове поле; `Combatant.ally = { n, kind }`, `kind` — id техніки, що їх поставила). Союзник має власні здоров'я, чакру, витривалість, ефекти, перезарядки, фази `wait → act → wait` і таймер; рух часу (`fightNextEventIn`, `step`, `handle`) обробляє його так само, як персонажа, після персонажа й у порядку появи. Рука союзника — техніки персонажа (`fight.kit`), крім тих, що діють на саме тіло чи бік (`summon`, `stance`); сумки, лікування й розхідників у нього немає (`view.pouch` порожній, предмети й лікувальні ефекти стосуються лише персонажа). Техніка з ефектом `{ kind: 'summon', fx }` (рядок `K.techFx`: `count`, `masteryStep`, `max`, `share`, `hp`, `dmg`, `threat`, `casts`) наприкінці касту забирає `share` поточної чакри й витривалості персонажа, ділить порівну між `count` тілами (+1 за кожні `masteryStep` рівнів Майстерності, до `max` живих разом), дає кожному `hp` від максимуму здоров'я персонажа й `dmg` від його ударів; дозволена `casts` разів за бій. Ворог на початку замаху обирає ціль серед живих тіл боку з потоку випадковості бою за вагою (персонаж 1, союзник `threat`; без союзників потік не чіпається), а наприкінці б'є її, якщо вона ще стоїть. Тіло з нулем здоров'я розсіюється: у цьому бою воно не з'являється, а його чакра й витривалість повертаються персонажеві (так само, коли бій скінчився, а тіло ще стоїть, і коли тілу нічим платити); програє бій лише персонаж. Те, що тіло зробило (використання технік, шкода, Майстерність), іде в загальний `tally` персонажа; шкода, яку воно отримало, у `taken` і Рани не рахується. Журнал: рядки союзника несуть `ally` (його номер), рядки ворожих ударів по союзнику теж. Збережений бій читається з `allies` і `allied`, якщо вони є (версію збереження це не змінює); читання перевіряє, що ідентифікатори й номери союзників різні, не збігаються з персонажем і ворогами, `kind` є технікою набору, а лічильник `allied` не менший за найбільший номер.
  - **Куди влучив удар.** Наслідки удару ворога (шкода, ухилення, оглушення важкого удару) лишаються на тілі, по якому його спрямовано: `heavyBlow` повертає це тіло (або `null` при промаху), оглушення Заклинача лягає на нього, а не на персонажа. Завершена дія записує тіло в `LastAct.target`, коли це не звичайний випадок (удар ворога по тілу, що не є персонажем, і ціль дії союзника; інакше поля немає, тож бій без союзників пишеться як завжди); інтерфейс малює цифру й «ухилився» на цьому тілі, а не на тому, що ворог обирає зараз. Інші гачки босів (`strike` суперника, туман двійника, ілюзія, повторне сховання) б'ють `fight.player` за задумом.
  - **Огородження охоплює бік.** Після виклику гачка іншого пакета перевіряються тіло гачка й усі тіла боку гравця (персонаж і союзники): зіпсований ефект чи таймер на союзнику так само скасовує бій (`void`), як на персонажі, і бій лишається придатним до збереження.
  - **Досвід.** Кожне тіло заробляє окремо, як будь-який виконавець (рішення автора): стиль персонажа (`tally.style`, 70% бойового досвіду) і його `masteryWork` задають лише його власні дії. Союзник має власні `ally.held` = `{ style, xp, work, last }`: стиль (навичка того, що він зробив останнім: техніки або простого удару), бойовий досвід за навичками (його нараховує кожен такт бою, `payTick`, за тим самим правилом часу й часткою `xpShare`, типово 1: із кількома тілами це може помножити бойовий досвід за годину) і робота Майстерності за техніками. Поки тіло живе, усе це лежить у ньому. Коли воно падає, розсіюється чи бій закінчується, `releaseAlly` переносить це в `tally.allyXp` / `allyWork`, а `payAllies` у `system.ts` виплачує персонажеві один раз (і чистить): досвід навичок і Майстерність, помножені на `passShare` (типово 1; 0 не передає нічого). Коли знання доходять до персонажа з його власного бою, вони втомлюють розум за правилом клонів (`fatigueFor`), помноженим на `fatigueShare` (типово 1, 0 вимикає). Усі три числа беруться з рядка `K.techFx` тієї техніки, що прикликала тіло (`ally.kind` → `effect.fx`, `combat/fight-allies.ts`), а не з жорстко вписаного рядка; менше нуля стає нулем; `releaseAlly` застосовує `passShare` і `fatigueShare` (друге лягає в `tally.allyTire`). Бій, що кінчається без розв'язки (зупинка дії, розвіювання клона, мисія), теж звільняє живих союзників і виплачує їхнє тим самим шляхом (`releaseFight` у `system.ts`), один раз; у бою клона вони лягають у `pending` клона (його знання) і втомлюють під час розвіювання, як будь-які знання клона. Позиція «найчастіше вжита техніка серед усіх тіл» не використовується. Бій без союзників пишеться як завжди: поля `held`, `allyXp`, `allyWork`, `allyTire` з'являються лише з союзниками. Місії (`missions/run.ts`) нараховують бойовий досвід підсумком бою й досвіду союзників не знають.
  - **Звикання.** Звикання ворога до техніки (`fight.uses`) спільне для всього боку: каст союзника привчає ворога до техніки так само, як каст персонажа. Це навмисно: ворог бачить техніку, а не того, хто її кинув.
  - **Таймери союзників.** Таймер, який гачок озброїв на союзнику, спрацьовує так само, як на персонажі (після таймерів персонажа).
  - **Ролі бойових клонів.** Вид даних `cloneRoles` (схема `cloneRoleSchema`; id `core:…` чи `<пакет>:…`; тексти — ключі `cloneRole.<id>.name` і `.desc`): `default` (рівно одна роль вмісту, перевіряє замкненість), `threat` (множник на `threat` клонів) і правило руки `hand` — `{ mode: 'copy' }` (рука персонажа, як було) або `{ mode: 'pick', size, weights: { damage, status, opens, cheap } }` (з відомих персонажеві технік, які клон може кинути, береться `size` найвищих за зваженою сумою; кожна величина віднесена до найкращої з кандидатів; `opens` — скільки комбо інших відомих технік чекають на стан, який лишає ця; нічия — за шкодою, потім за id). Вибір роботи й числа лежать у даних, у ядрі їх немає (`combat/fight-roles.ts`, без випадковості). Один вибір на всіх клонів — `state.loadouts.cloneRole` (`null` — роль за замовчуванням; команда `loadout.cloneRole`; невідомий id вмісту лишається в стані, а бій грає роль за замовчуванням; id зниклого пакета іде в кошик `dormant` як `single`). Бій читає роль, коли його починають (`PlayerSnapshot.cloneRole`): у `PlayerKit` лише для ролі, що не збігається з типовою, пишуться `cloneHand` (рука клонів), `cloneThreat` і `cloneRole`, тож бій із роллю за замовчуванням записується байт у байт, як до ролей, а збережений бій несе свою руку й не залежить від вмісту. Клон із `cloneHand` може кидати техніку поза спорядженням персонажа; техніки, що діють на тіло чи бік, і ті, що потребують стійки, у руку клона не потрапляють.
  - **Техніка-призов у даних.** Імпорт знімає з призову (`core:shadow_clone`) тег `area` і ставить `noDamage`: її сторінка не показує шкоди, вона не відповідає ні на яку рису, а підготовлена рука рахує її за тілами, а не за шкодою: `count × dmg` від найкращої атаки на вибір (`summonShare` у `loadout.ts`, числа з `K.techFx`).

### Моди інтерфейсу

Мод може змінювати не лише вміст гри, а й вигляд та поведінку інтерфейсу: тему, додаткові показники, посилання, сторінки, навігацію. Модель двошарова.

**Стабільний шар** — те, що гра обіцяє зберігати між версіями:

- **Токени.** Усі кольори, шрифти, розміри шрифтів, відступи, радіуси, товщини меж, висоти контролів, розміри іконок і ширини розкладки, `z-index`, тривалості переходів — CSS-змінні з `apps/web/src/tokens.css`; у стилях компонентів сирих довжин немає (тест `no-raw-lengths`: лише `0`, `1px`, `100vw`, брейкпоінти медіазапитів і приватні змінні компонента `--_назва`, що живуть у його `<style>`). Назви ролей, не значень; публічних токенів довжини й розміру — не більше 60. Група — контракт: значення можна змінювати темою, назви не зникають.

  | Група | Токени |
  | --- | --- |
  | Відступи | `--space-1 … --space-8` (0,25 · 0,5 · 0,75 · 1 · 1,25 · 1,5 · 2 · 3 rem) |
  | Текст | `--text-2xs, -xs, -sm (основний), -md, -lg, -xl, -2xl, -display`, `--font-mono`, `--leading-tight, -normal, -loose`, `--tracking-wide` |
  | Радіуси | `--radius-xs, -sm, -md, -pill` |
  | Межі | `--border-thin, -thick, -heavy`, `--focus-offset` |
  | Контроли | `--control-xs, -sm, -md` — мінімальний розмір усього, що натискають; зміна змінює всі кнопки, поля, списки й пункти навігації |
  | Іконки | `--icon-xs, -md` |
  | Смуги | `--bar-thin, -md, -thick` |
  | Розкладка | `--sidebar-width, --meta-width, --topbar-height, --tabbar-height, --now-height, --tile-min, --card-min, --panel-min, --modal-width, --toast-width, --measure` |
  | Шари й час | `--z-raised, -overlay, -popover, -popover-top, -toast, -modal`, `--duration-fast, -base` |
- **Слоти.** Іменовані точки вставки; список із типами контексту — `lib/ext/slots.ts` (`SLOT_NAMES`, `SlotContexts`): `skill.header`, `skill.footer` (`{ skill }`), `action.tile` (`{ action }`), `now.bar` (`{ slot }`; у «Зараз» лишаються місце й бафи, щойно показано загін), `squad.row` (`{ performer, slot }` — у рядку виконавця панелі «Загін»; `performer` 0 — персонаж, далі номер клона), `goal.panel`, `entity.sections` (`{ ref }`, після кожної сторінки сутності, зокрема загальної, і в кінці аркуша деталей), `sidebar.skill` (`{ skill }`), `topbar`, `settings`, `village.header`, `missions.header`, `mission.header`, `mission.footer` (`{ mission }` — ідентифікатор місії), `map.panel` (`{ hex, cell }` — ключ `q,r` гекса й id клітинки на ньому, коли гекс розвіданий; у кінці панелі гекса на мапі; точки інтересу місць виводить сама панель, див. частину `point-row`), `page.footer` (`{ route }`), `fight.arena` (`{ target }` — зона чи операція бою, `null` для бою місії; під ареною бою), `prep.verdict` і `prep.footer` (`{ target, level, hand, suggested }` — ціль підготовки, наскільки її знає гравець, нинішня рука й набір, який гра порадила; під вердиктом і внизу екрана підготовки), `bingo.entry` (`{ enemy, level }` — у записі Бінґо-книги про ворога, якого гравець зустрів).
- **Частини (anchors).** Кожен змістовний елемент має `data-ui="<частина>"`, а якщо він представляє сутність — `data-entity="<вид>:<id>"` (і `data-slot-index` для нумерованих місць). Список частин — `lib/ext/parts.ts` (`UI_PARTS`, `ENTITY_PARTS`): сторінка (`page`, `data-page` — ключ сторінки), аркуш деталей сутності (`sheet`; `data-entity` — крім невідкритої сутності), хлібні крихти (`breadcrumb`), пункт навігації, рядок навички, плитка дії, її емблема (`action-emblem`) та смуга, показники й Майстерність, смуга пулу, рядок вимоги, слот «Зараз» і позначка клона в ньому (`clone-tag`), панель «Загін» (`squad`), її рядок виконавця (`squad-row`; `data-for` — вид дії) з меню виконавців (`performer-menu`), пункт «Новий клон для цієї дії» (`clone-start`), позначки виконавців на плитці (`performer-marks`, `performer-mark`), попередній перегляд розвіювання (`dispel-preview`), перемикач боїв (`fight-switcher`), частина офлайн-звіту про одного виконавця (`report-performer`); фігури клонів на мапі мають частину `map-token` з `data-performer`, панель «Мета», заголовок і секції сторінки сутності, інгредієнт, товар, предмет банку, картка будівлі, мапа (`map`), гекс мапи (`hex`; `data-hex` — координати `q,r`, `data-state` — `here`, `fog`, `reach`, `marked`, `partial` або `full`), фішка гравця (`map-token`), панель гекса (`hex-panel`), рядок точки інтересу клітинки (`poi-row`), точка інтересу місця в панелі гекса (`point-row`; `data-point-status` — `veiled`, `open` або `found`, `data-point` — місце, для прихованої його немає), маркер точки на гексі мапи (`map-point`), блок майстерності мапи на сторінці Розвідки (`map-mastery`), картка місії (`mission-card`), арена бою (`fight-arena`), боєць арени (`fighter`; `data-side`, `data-entity` для ворога, що відкритий), дія бійця з її смугою (`fight-action`; `data-phase`, `data-action`), результат дії (`fight-outcome`; `data-kind` = `pop` — число, що злітає з цілі приблизно на секунду, або `last` — рядок «остання дія» під бійцем), рука (`prep-hand`), блок «Захист» (`prep-defence`), вердикт (`prep-verdict`; `data-verdict`), запис Бінґо-книги (`bingo-entry`; `data-entity`), етап місії (`mission-stage`, `data-stage` — його номер), винагорода місії (`mission-reward`), булавка мети (`pin-goal`; з нею `data-entity` і `data-pinned`: кутова іконка плитки, підпис під деревом вимог або кнопка сторінки сутності), валюта верхньої смуги, модальне вікно. Частини й слоти — разом публічний контракт. Секція «Застосунок» сторінки налаштувань (PWA) — віджет слота `settings`, зареєстрований пакетом `core`.
- **Пакет інтерфейсу** — `UiPack = { id, theme?, setup?(ui: UiRegistrar), start?(api) }`. Застосунок стартує зі списком пакетів (`<App uiPacks>`, типово `[coreUi]`); реєстри створюються на кожен запуск і передаються контекстом Svelte, глобальних реєстрів немає. Усе має ключ `<packId>:<id>`; дубль — помилка з назвою пакета.
- **Реєстратор.** `addWidget(slot, widget, { id?, order? })`, `addPage({ id, route, title, mount, nav?, crumbs? })`, `addSheet(kind, { parent, home?, mount? })`, `addNavItem({ id, group: 'tab' | 'side' | 'main', title, icon, route, order, tabOrder?, tab? })`, `addEntityLink({ kind, title, href | mount })`, `addSetting({ id, title, kind: 'toggle' | 'select', options?, default })`, `addTheme({ id, name, tokens, css? })`, `addLocale(lang, map)` — ключі лише `x.<packId>.…`, `addStylesheet(css)`. Маршрути сторінок пакета — `#/x/<packId>/<сторінка>` (шаблон: `:name` — один сегмент, `*name` — решта). Поле `tab` пункту — ідентифікатор пункту панелі вкладок, до якого він належить на телефоні: його сторінки підсвічують ту вкладку (а не «Ще»), і маркер «наступного кроку» вказує на неї; так сторінка пакета може жити всередині чужої вкладки. Вбудований пакет `core` реєструє свої сторінки й пункти навігації тими самими викликами (`lib/ext/core-ui.ts`).
- **Віджет не залежить від Svelte:** `(el: HTMLElement, api: UiApi, ctx) => void | (() => void)`; `svelteWidget(Компонент)` — перехідник. Віджет, що кидає помилку під час створення, оновлення чи прибирання, не ламає сторінку: його не показано, одне `console.warn` на віджет.

- **Помилки пакетів не зупиняють гру.** Усе, що надає пакет (хуки, предикати, будівники посилань, віджети, спостерігачі, підписки), викликається через один охоронець: помилка ловиться, дає одне попередження, а виклик повторюється наступного разу; після трьох невдач поспіль його вимкнено. Списки (групи навичок, природи, ранги, валюти, види сутностей) ітеруються з контенту; назви беруться з локалі пакета-власника, а відсутній текст показує людський замінник id (останній відрізок: `ember_pulse` → «Ember pulse») і один раз пише в консоль у збірці розробника — сирого ключа на екрані немає. Відсотків і числового порівняння наборів у базовій грі немає. Прогноз іде частинами: одна одиниця `stepAnalysis` — це один бій першого прогону (чи один прохід операції) або шматок сесії завдовжки `SESSION_STEP_MS` ігрового часу (сесія відтворюється на копії стану, а `advance` не залежить від розбиття, тож результат той самий, що й за один прохід), тобто кілька мілісекунд роботи; між частинами потік повертається браузеру (`lib/analysis-runner.ts`, бюджет шматка `SLICE_MS`). Прогнози вбудованого екрана підготовки й симулятора залежать лише від зведення своїх справжніх входів (ціль, рука, сумка з тим, що додає банк, Рани, ранг, число відомих технік, рівні навичок), а не від кожного оновлення стану: такт гри не перезапускає прогноз. На телефоні (до 768 px) арена стискається: одна колонка, ціль гравця (`targetedKey`) одразу під гравцем, нерухомий рядок гравця, тіла без цілі — ім'я, здоров'я й дія в рядок-два; верхня смуга — один рядок із кнопкою меню.
- **Панелі навичок (D4).** Що показує сторінка навички, визначає `skill.activity` з контенту, а не id: `addSkillPanel(activity, { mount?, place?: 'replace' | 'after', hint? })` реєструє панель (Svelte-компонент або віджет-функцію; Svelte-панель отримує проп `skill`) і підказку сторінки. `coreUi` реєструє панелі для `map`, `course`, `insight` і підказки для `patch`, `recipe`, `station`; навичка, чия діяльність не має панелі, показує загальний список плиток дій. Пізніший пакет заміщує попередній, із попередженням.
- **Точки інтересу (D6).** `addPoiRenderer(kind, { icon, mount? })` задає значок і рядки під назвою для точок інтересу цього виду (контекст `{ poi, cell }`); `coreUi` реєструє вісім відомих видів. Вид без рендерера малюється загально: значок-мітка, назва, опис і посилання на сутності, названі в полях точки. Панель пакета, що падає під час відмальовки, лишається поза сторінкою (`svelte:boundary`, одне попередження), як і віджет.
- **Аркуші деталей (W1).** Листкова сутність із природним батьком — техніка, вправа, практика, перешкода, рецепт, предмет, спорядження, будівля — не має сторінки: `#/<вид>/<id>` малює сторінку батька й поверх неї аркуш `EntitySheet` (на широкому екрані панель праворуч, сторінка поруч звужується й лишає плитку в полі зору; на телефоні — на весь екран з кнопкою «Назад»). Плитка сутності на сторінці батька підсвічується (`data-highlighted`) і прокручується в поле зору. Фокус заходить в аркуш, не виходить із нього на Tab; Escape й Назад закривають його, фокус повертається на елемент, що його відкрив. Батько — дані виду: `addSheet(kind, { parent, home, mount? })`, де `parent` — хеш або функція `(ref, { content }) => хеш | null`, а `home` — хеш для сутності, якої гравець не відкрив, або id, якого немає в контенті (справжній батько видав би, чому вона належить); `home` обов'язковий разом із функцією. Без `mount` вміст аркуша — загальна `EntityPage`. Вид без аркуша лишається сторінкою (зареєстрованою або загальною). Правило відкриття діє на аркуш: невідкрита сутність дає аркуш «Ще не відкрито» без id у DOM, сутність за назвою — аркуш за назвою. Вбудовані батьки — `lib/sheet-parents.ts` і `core-ui.ts`: техніка, вправа, практика, перешкода, рецепт — сторінка своєї навички; предмет — сторінка навички, що його збирає (трава), інакше банк; спорядження — крамниця; будівля — село. Сторінки, що лишаються сторінками (місія, регіон і клітинка, доручення, іспит, загальна), мають хлібні крихти над собою (`PageSpec.crumbs`): розділ із пункту навігації сторінки (`nav`), далі сутність; загальна сторінка без розділу починається з «Головна» й назви виду.
- **Види сутностей (D6).** Кожен вид із `content.entityKinds` має маршрут `#/<вид>/<id>`: зареєстрована сторінка або загальна `EntityPage` (назва, опис, значок, дерево умов із `unlockReq`/`unlock`/`req`, посилання на сутності з полів даних, слот `entity.sections`); невідомий id дає стан «Не знайдено». Секція крамниці — будівля, чиї вимоги відкривають товар (назв будівель у коді немає); зв'язки «де вчать» — `duty: 'teaching'` і `duty: 'scrolls'` будівель та `item.scroll.source`; значок ресурсу села — поле `resource.icon`; колір значка стану — поле `status.nature`.
- **Перевірка.** `testmod` (`apps/web/dev-packs/testmod-ui.ts`) несе тему, віджет «досвід за годину, час до наступного рівня й до максимуму» на сторінці навички, сторінку, пункт меню, посилання на сторінках технік, налаштування, рядок у кожній плитці дії через `dom.observe`, хуки `command:after`/`command:before`, обгортку сторінки налаштувань і прибирання пункту меню. Тести монтують застосунок із цим пакетом і без нього.

**Необмежений шар** — без обіцянок стабільності:

- **Вставка будь-де.** `api.dom.observe(ціль, mount)`, де ціль — CSS-селектор або `{ part, kind?, id? }`: `mount(el, api)` викликається для кожного елемента, що збігається зараз чи з'явиться пізніше (один `MutationObserver` на корені застосунку), і може повернути прибирання, яке виконається, коли елемент зникне чи пакет вивантажать. `api.dom.root` — корінь застосунку.
- **Прямий доступ.** Пакет може користуватися `document`, власним CSS (`theme.css`, `addStylesheet`) і чим завгодно: `UiApi` — зручність, а не межа безпеки. Назви класів і структура DOM поза частинами `data-ui` можуть змінитися з будь-яким оновленням гри — CSS і вибірки за ними ламаються на ризик автора мода.


У MVP пакети збираються під час збірки застосунку: є токени, реєстри, слоти й `testmod`. Встановлення сторонніх модів гравцем, mod.io, ізоляція скриптових модів і версіонування API модів — після MVP.

## Напад на село

Напад — сутність `raids` у пакеті (`core:raid_grey_bands`), а не код: у ядрі немає ні його id, ні числа груп, ні будівель. Поля: `trigger` (дерево вимог; напад кличеться раз, коли воно виконується — у `core` це `{ t: 'quest', id: 'core:outskirts', step: 3 }`, тобто крок 4 ланцюжка став активним), `enemy` (ворог кожної групи), `packs`, `lead` і `hold` (тіки села: до приходу й скільки напад чекає біля складів), `defence` (внески захисту цілими очками: рівень будівлі або одиниці ресурсу), `perPack` (очок на одну групу), `autoShare`, `targets` (будівлі в порядку, у якому їх ушкоджують групи, що прорвалися), `repair` (тіків ремонту), `reward` (`ryo`, `rep`).

Стан — `village.raids[id]` (`warned` → `active` → `over`; лічильники відбитих гравцем, відбитих селом, прорваних, ушкоджених будівель, виплачене) і `village.damage[будівля]` (тіків до ремонту). Усе йде в тіках села й у вбивствах бойового циклу, тож не залежить ні від нарізки часу, ні від того, чи гравець онлайн. Прапори: `raid.<id>.active` (поки напад біля складів) і `raid.<id>.over` (його може питати крок ланцюжка); їх пише ядро й перераховує завантаження з фази.

- `startRaids` кличе напад у ту мить, коли крок став активним (наприкінці `updateQuests`), і в `syncVillage`.
- Гравець б'ється дією `fight` з id нападу (`fightTarget` знає id нападу; вимога дії — прапор `active`, тож бій сам зупиняється, коли напад скінчився). Кожна перемога над групою рахується (`raidPackFell` у `victory` бойової системи); остання група завершує напад і бій.
- Коли `hold` минув, село забирає групи, що лишилися, у кількості `⌊захист ÷ perPack⌋` — лише якщо захисту вистачає хоча б на одну групу (`⌊захист ÷ perPack⌋ > 0`). Інакше (захисту немає або він замалий) напад чекає гравця (так офлайн «небезпечні події відбуваються лише за наявності захисту»).
- Тексти нападу — з даних: назва `raid.<id>.name` (її беруть загальні рядки панелі, тостів і звіту), нападники — посилання на `enemy`, цілі — посилання на будівлі `targets`, захист — складники `defence` за їхніми назвами; у загальних рядках інтерфейсу немає назв вмісту. `village.raids` і `village.damage` — місця таблиці `dormant-places.ts` (правило `keys`): напад мода, що ззовні пакета завантажили без нього, повертається разом із ним із фази, а не кличеться знову.
- Звіт про час, коли гравця не було (`OfflineSummary.raids`), каже, що напад прийшов або скінчився.
- Кожна група, що прорвалася, зупиняє на `repair` тіків одну збудовану будівлю з `targets`: вона не виробляє, не дає бонусів і не рахується в захисті, її рівень лишається (`village.damage`; `effectiveLevel`, `villageProvider`, `treasuryIncome`). Запаси, казна й склад не зменшуються.
- Нагорода — `reward`, помножена на частку груп: відбиті гравцем рахуються за 1, відбиті селом — за `autoShare`.
- Міграція v18 → v19 дає селу порожні `raids` і `damage`; напад, якого вимагає крок ланцюжка, що вже пройдено, стає завершеним без нагороди й ушкоджень і не кличеться знову. Завантаження приводить усе до меж даних і пише прапори з фази.

## Світ: гекси, розвідка, подорож

Світ — сітка гексів (pointy-top, осьові `q`, `r`), дані контенту: `hexes` (ключ `"q,r"`; гекс із `terrain` ігровий, без нього — лише малюється, без `country` — відкрите море), `terrains` (словник; `blocked` — не можна ступити), `countries`, `places` (названі місця на гексах: назва й історія `place.<id>.name/desc`). Числа — `K.map`: `terrain[id] = { walkMin, survey }` (хвилини на гекс, множник часу розвідки), `range` (дальність розвідки за рівнем Розвідки), `outpostRange`, `startRadius`, `plainSurvey`, `plainScout`. Клітинка зрізу — значущий гекс (`cell.hex`); решта гексів — прості. Координата має одного власника: два пакети з одним `q,r` — помилка складання; замкненість перевіряє, що клітинки й місця стоять на ігрових гексах, що клітинка одна на гекс і що кожен рельєф має числа. Земля пакета — окремий острів (сітка зайнята): дороги між островами в MVP немає.

**Виконавці й позиції.** Кожен виконавець (персонаж і, згодом, кожен тіньовий клон) — окрема фігура на мапі зі своєю позицією, прив'язаною до індексу слота дії. Слот 0 — персонаж: його позиція — `world.location`. Позиції решти — `world.figures[індекс слота]` (необов'язкова гілка, читається порожньою; клон з'являється там, де стоїть персонаж, коли в його слот ставлять дію (`startAction` пише `figures[слот]`; нова дія клона, що вже працює, лишає його на місці), і йде далі сам. Зупинка слота, крім заміни дії (розвіювання, ручна зупинка, відмова), прибирає фігуру (`removeFigure` у `stopSlot`): на мапі малюються лише фігури слотів, що працюють, а наступний клон знову починає там, де стоїть персонаж. Клон, що **дійшов**, не зникає: подорож (`walkKind.after`) передає його слот дії `stand` («Стоїть на місці», `STAND_KIND`, id `here`): вона нічого не робить, лише тримає слот, тож фігура лишається на гексі, а клон і далі стоїть (майже не витрачаючи чакри), поки його не розвіють чи не дадуть іншу дію (клон стоїть і на місці сили, див. нижче). Завантаження відкидає фігури слотів без дії. Слот без запису читається позицією персонажа). Читати позицію — `positionOf(state, slot)`, ставити — `placeAt`. Усі дії мапи (`explore`, `walk`, `autosurvey`) і вибірки (`positionHex`, `cellAtPosition`, `surveyRange`, `surveyAccess`, `routeTo`, `travelBlocked`, `travelPlan`, `hexInfo`, `listHexes`, `autoPlan`, `rangeNow` …) приймають слот (останній параметр, типово 0): дальність розвідки міряється від позиції того, хто розвідує, шлях рухає лише виконавця свого слота, авторозвідка планується для кожного слота окремо й не бере гекс, який розвідує інший слот. Подія `hexEntered` і контекст хука `rules.hexEntered` мають поле `slot`.

Стан: `world.location` — **адреса** гекса (id клітинки, що на ньому стоїть, або ключ `q,r`); `world.explores` — кількість розвідок за адресами; `world.surveyed` — ключі розвіданих гексів; `pois`, `claimed`. Гекс **розвіданий**, коли досяг першого рівня розвідки (клітинка — `K.cellExplores[0]`, простий гекс — `K.map.plainSurvey[0]`) або позначений так (стартова зона, міграція). Нерозвіданий гекс — туман: у нього не можна ступити, маршрут не йде крізь нього, рельєф невідомий. Про гекс у тумані інтерфейс не каже нічого: ні назви клітинки на ньому, ні посилання, ні рельєфу, ні рівнів і кількості розвідок (`hexInfo` дає їх нулями, `address` лишається лише для команд); дію на такому гексі Now-панель, тости й посилання називають «гекс у тумані» (`actionRef`), адреса `#/cell/<id>` клітинки в тумані не ставить мапу на її гекс. Відомі лише час розвідки й контур дальності, що залежать від прихованого рельєфу (залишок, див. issue).
- **Землі пакета.** Пакет робить придатним для гри гекс сітки (відкрите море чи чужу землю) патчем `{ target: { kind: 'hexes', id: 'q,r' }, set: { terrain, country } }` (змінити можна лише ці два поля; два пакети не міняють те саме поле) і додає звичайні клітинки, місця й точки на нього. **Зв'язок** (`links`, список із id: `a`, `b`, `minutes`, `kind`) єднає два гекси, що не є сусідами (переправа, перевал): для маршруту й розвідки кінці зв'язку — сусіди; з одного кінця можна розвідувати інший, хоч би він був поза дальністю; перейти на кінець, який ще в тумані, не можна. Замкненість: обидва кінці — придатні для входу гекси, кінці різні й не сусідні, пара не повторюється. Мапа малює зв'язок пунктиром і обмежує масштаб землею, яку гравець може знати (розвіданою, її сусідами й кінцями зв'язків), тож далекий острів пакета не стискає мапу. Малюнок рельєфу — дані: `terrain.glyph` (контур SVG в одиницях гекса) і `glyphFill`; код інтерфейсу не знає id рельєфів. Розвідані прості гекси пакета, що зник, губляться при завантаженні (прийнята прогалина MVP); розвідані клітинки зберігаються.

- **Розвідка** (`explore`, id — адреса). Можна розвідувати гекс у межах `surveyRange` від позиції (дальність росте з рівнем Розвідки за `K.map.range`, застава з розвіданою точкою дає ще `outpostRange`); гекс не мусить бути сусіднім, але мусить бути розвіданим або торкатися землі, куди можна дійти (інакше `error.cutOff`; за межею — `error.outOfRange`). Простий гекс має `plainSurvey.length` рівнів і час розвідки `K.explore` × множник рельєфу; клітинка має свої рівні, час, Intel і точки інтересу без змін.
- **Подорож** (`walk`, id — адреса цілі; команда `world.travel`). Гра сама обирає найкоротший за часом маршрут розвіданими гексами (`routeTo`, Дейкстра за `walkMin` і хвилинами зв'язків; нічия — менший ключ; пошук і план авторозвідки запам'ятовуються для стану й забуваються, коли змінюється розвідана земля, рівень, позиція чи вимоги: `touchWorld`, `worldStamp`; 12 годин авторозвідки коштують як 12 годин практики); гравець обирає лише ціль. Дія займає слот і йде гекс за гексом (`complete` повертає `step`, доки не дійшла): позиція оновлюється на кожному гексі, тож зупинена подорож лишає на останньому досягнутому. На кожен гекс: подія `hexEntered { hex, terrain, by: 'walk' }` і обробники `rules.hexEntered` (упорядкований список `HexEnteredHook`; у вбудованих правилах один — `walkHook` із `finds.ts`; `addRule(rules, 'hexEntered', fn)`; обробник пакета, що кидає, не зупиняє подорож, вимикається для цього стану і дає один `ruleDisabled`; обробник, що пересунув виконавця чи годинник, відкочується: `enterHex` повертає позиції й `now` після кожного обробника). Поле `by` події й контексту — `walk` (крок подорожі чи авторозвідки), `paid` (за рьо) або `outpost` (між заставами). Після прибуття — `travelled`. Подорож, що не потребує часу (за рьо чи заставами), — окрема команда, див. «Точки інтересу».
- **Авторозвідка** (`autosurvey`, id `vision`). Кожен цикл: найближчий гекс у межах дальності, що ще не досяг межі рівнів і чиї вимоги виконано (спершу ті, що в тумані, потім поглиблення розвіданих; більш розвіданий раніше; менша адреса), розвідує його; коли в межах нічого немає — іде до найдешевшого місця, звідки щось можна розвідати. Зупиняється з `error.nothingToSurvey`, коли розвідувати нічого.
- Стартова зона: гекси в `K.map.startRadius` від першої клітинки розвідані; прості — з рівнем 1, клітинки лише позначені (їхній рівень і точки здобуваються розвідкою). Міграція 16 → 17 розвідує те саме, плюс усі гекси регіонів, де розвідано клітинку, і прямі лінії від першої клітинки до їхніх клітинок (щоб туди можна було дійти).
- Нових полів на гекс немає, окрім `explores` і `surveyed`; щоб додати посібне поле гекса (таймер поповнення), заводь нову необов'язкову гілку поруч, що читається порожньою, коли її немає.

### Точки інтересу, дорога, платна подорож

**Точка інтересу** — дані місця (`Place.point`, схема `pointSchema`; ідентифікаторів і видів у ядрі й UI немає, пакет дає точку будь-якому місцю чи додає місце з нею; вбудовані точки лежать в `data/hand/place-worth.json`). Поля: `reward` — **нагорода за відкриття** (`payoutSchema`: рьо, предмети, інші валюти за id — Intel, трохи досвіду навички); `power` — модифікатори, **місце сили**; `travel` — група безкоштовного переходу, **застава**; `revealedBy` — **прихована точка**: гекс розвіданий до рівня `survey` або знайдена точка місця `point` (досить одного); `needs` — **вимога** (дерево вимог; текст підказки `place.<id>.hint` обов'язковий, замкненість це перевіряє). Місце без `point` — просто місце. Місця «дій, що відкриваються» немає як поля: дія просить прапор `point.<id місця>` (`{ t: 'flag', id: pointFlag(place) }`); вимога читає `world.pois`, прапор у `state.flags` не пишеться (префікс `point.` зарезервований у `requirements.ts`). Так рідкісні трави вбудованого пакета (`herb-reqs.json`) просять Ліс Джофуку й Святе місце біля водоспаду (вогняна квітка Пекельної долини лишилась вільною: бот симуляції не ходить мапою, і поріг продажів ремесла вийшов би за межі; рішення за етапом балансу).

Стан: `world.pois[<id місця>]` — точка знайдена (поряд з точками клітинок). Стан точки для гравця — `pointStatus`: `hidden` (гекс не розвіданий до рівня 1, не виконано `revealedBy`: гекс **не виказує** ні місця, ні точки, ні назви: `hexInfo.places` і `points` її не містять), `veiled` (виконано `revealedBy`, але не `needs`: `hexInfo.points` дає лише ключ підказки, без id місця), `open` (можна знайти, ступивши), `found`. Знаходить `settlePoints`: її кличуть `enterHex`, кінець розвідки й система `points` (id `points`, без власних подій) після кожної події гри, тож точка, відкрита під ногами виконавця (рівнем розвідки, знахідкою, виконаною вимогою), знаходиться без виходу й повернення і не залежить від того, як нарізано час. Нагорода платиться **до** позначки «знайдено» (бонус місця не множить власну нагороду) і лише раз. Точки на стартовому гексі гра знає з першого дня без нагороди (`createWorld`).

**Виконавці.** `performers(state)` — персонаж і кожен клон, чий слот має дію (його фігура на мапі). Читають її модифікатори місць сили (`pointsProvider`): поки виконавець стоїть на гексі знайденої точки з `power`, її модифікатори діють лише на дії цього виконавця (`actingPerformer()`: чия дія рахується; рішення автора 18.11); бонуси різних точок складаються лише для того, хто на них стоїть; джерело — ключ `place.<id>.name` (рядок джерела в розкладі). Те саме для тренувальних точок клітинок. Клон, що дійшов і стоїть, не дає бонусу нікому, крім власних дій.

**Подорож.** `world.travel { cell, mode, slot }`: `walk` (типово) — пішки, безкоштовно, за час, офлайн теж; `paid` — миттєво за рьо до розвіданого гекса, до якого ведуть розвідані гекси (ціна `travelPrice` = `max(K.map.travel.min, ⌈K.map.travel.ryoPerMinute × хвилини маршруту при повній швидкості × модифікатор travel.price⌉)`: росте з відстанню й рельєфом; у тумані — `error.cellNotReachable`, нестача рьо — `error.notEnoughRyo` з `params.price`); `outpost` — миттєво й безкоштовно з гекса, де виконавець стоїть на знайденій заставі, на знайдену заставу тієї ж `travel`-групи (`outpostTargets`; `error.notAtOutpost`, `error.notOutpostTarget`). Миттєва подорож (`jumpTo` у `travel.ts`) рухає лише виконавця слота, що просить: його дія замінюється (клон після неї стоїть, дія `stand`), події `hexEntered { by }`, `paidTravel`, `travelled`; на шляху нічого не платить (ні досвіду, ні знахідок). `travelPlan` дає `price`, `paidBlocked`, `free` для інтерфейсу.

**Дорога.** Вбудований обробник `walkHook` (`finds.ts`) платить кроки подорожі (`by === 'walk'`): досвід Атлетики й Розвідки за гекс — `rate(K.map.walk.athLevel | scoutLevel) × хвилини рельєфу`; дрібні знахідки рельєфу (`Terrain.finds`: шанс на гекс, потім предмет за вагами; потік RNG `world`) і **рідкісні знахідки** місць (`Place.rare`: у радіусі `radius` шанс `chance` на гексі місця спадає лінійно до `chance / (radius + 1)` на крайньому колі; запас `stock`, відновлюється по одній за `restockMs` ігрового часу; стан — `world.stock[місце] = { left, at }`, ліниво: відновлення рахується з `state.now`, тож офлайн і нарізка часу його не змінюють; порожній запас RNG не торкається).

**Майстерність мапи.** `K.map.mastery`: щаблі за кількістю гексів, розвіданих до найвищого рівня (число або `all` — усі ігрові гекси); досягнутий щабель додає свої модифікатори (джерело — ключ `mod.source.mapMastery`). `mapMastery(state)` дає лічильник і щаблі; лічильник кешується до зміни ревізії розвіданої землі (`worldRevision`).

**Авторозвідка** серед рівних за туманом бере спершу гекси, де є точка, **відома гравцеві** (`knownPoint`: прихована не виказується порядком).

Стан версії не змінився (нові гілки `world.stock` і ключі `world.pois` необов'язкові й читаються порожніми; завантаження відкидає чуже), тож міграції немає: `STATE_VERSION` лишається 17.

## Збереження

`{ v, savedAt, state }` у JSON; `savedAt` — настінний час, який дає адаптер платформи. Міграції — масив функцій `v → v+1` (поточна версія — 22; існуючі номери не перенумеровуються; міграція v20 → v21 додає `loadouts.cloneRole = null`; міграція v21 → v22 міняє кущ трав `{ stock, size, carry }` на `{ stock, size, at }`: `at` — час гри, від якого йде годинник відростання; кущ із травами починає його «зараз», порожній зараховує вже прожиту паузу). Міграція v15 → v16 прибирає навичку «Ухилення» (записи `skills.eva`, `pools.eva`) і бій, що йшов: він не може тривати в новому циклі, тож дія «бій» починає свіжий без нагороди, Рани й втрати предметів. Збережений бій зі старими полями (`idle`, `recover`, `intervalMs`) `parseFight` так само відкидає.

**Пакети в збереженні.** `state.packs` (`{ id, version }[]`) і `state.rankOrder` пишуться з `content` при створенні й при кожному завантаженні. Завантаження ніколи не кидає через відсутній пакет:
- id, яких контент не знає, відкидаються з усіх гілок, а те, що належало пакету, що зник (за префіксом `<пакет>:` у ключі), переходить у кошик `state.dormant[<id пакета>] = { version, rank, natures, data }`, де `data` — записи гілок `skills`, `pools`, `mastery`, `bank`, `currencies`, `known`, `flags`, `counters`, `quests`, `gear`, `bushes`, `meditation`, `buffs`, `bingo`, `report`, `shown`. Не зберігаються в кошику: дослідження клітинок, рівні будівель і побудовані перешкоди пакета;
- ранг пакета, що зник, замінюється найвищим відомим рангом, що йшов раніше за збереженим `rankOrder` (кошик зберігає сам ранг); природи, яких немає, відкидаються (кошик зберігає повний список);
- коли пакет повертається, його кошик повертається у гілки (запис, що вже є, перемагає), ранг повертається, якщо він вищий за поточний, природи зливаються, кошик видаляється;
- пакет, якого раніше не було, ініціалізує свої навички й валюти нулями; зміна складу пакетів дає подію `packsChanged { added, removed }` (для збереження без списку пакетів події немає);
- кошики недовірені: id пакета перевіряється й не може бути назвою члена `Object`, гілок і записів обмежена кількість, ключі й тексти обмежені за довжиною, числа відсікаються на 10^15, значення — звичайний JSON обмеженої глибини. Усі пошуки за ключами зі збереження (`action.kind`, навички, валюти, прапорці) — через власні властивості, тож `constructor` і `__proto__` нічого не ламають. Веб-адаптер пише в IndexedDB раз на 10 с і при згортанні вкладки; експорт і імпорт — рядком base64. Офлайн: при завантаженні `advance` на `min(зараз − savedAt, 12 год)`.

## UI

- Svelte 5 з рунами, без SvelteKit; власний мінімальний хеш-роутер.
- Сховище `game.svelte.ts` тримає стан у `$state.raw` і лічильник оновлень; цикл гри викликає `advance` і збільшує лічильник 10 разів на секунду.
- Кольори, шрифти, відступи — лише CSS-змінні з документа про візуальний стиль.
- Тексти — `t(key, params)`; українська множина через `Intl.PluralRules`.
- Іконки — компонент `Icon` із реєстром SVG; техніки без власної іконки отримують складену: колір природи, знак ролі.

- **Смуги часу.** Кожен візуал часу (смуга плитки, походу, каст бою, печатки, спалах емблеми) читає `--tp` і рухається спільною примітивою `lib/time-progress.ts` (`ProgressTiming { fraction, cycleMs, running }`): на кожне оновлення сховища — одна лінійна Web Animation до 1, перезапуск лише за розбіжності понад `RESYNC_THRESHOLD`. Час каста завжди з селекторів ядра, а розбиття інтервалу на фази — у `lib/timing.ts`.

### Типова Майстерність захисних технік і пороги тіру ШІ

Рейтинг ухилення не має члена за рівнем гравця: його складають ранг, захисні техніки, спорядження й знання про ворога. Смуги влучань («типовий» персонаж: обидві криві влучань, ворога в нього й його у ворога, на рівнях 1–50 у межах ±5 пунктів від кривих бази `dev` на 3f559af; у цьому PR 48–56% і 59–65%) рахуються для персонажа, чия Майстерність кожної захисної техніки виведена з годин гри (`typicalDefenceMastery` у `packages/sim/src/character.ts`: 15% часу практики віддано захисним технікам, 10 навичок у тренуванні, плоска `YARDSTICK_MASTERY_PER_HOUR` замість справжнього темпу за рівнем: вона ввімкнена навмисно, похибка не більша за 0,4 пункта шансу влучання ворога), для «занедбаного» (Майстерність 1) й «повного» (стеля). Пороги тіру ШІ ворога за бойовим рівнем (`K.ai.enemyTier`: генін від 8, чунін від 35) — дизайн, а не змінна підгонки. Набір підгонки: `packages/sim/scripts/fit` (README); криві: `packages/sim/scripts/hit-curves.ts`.

### Дієвий рівень захисної техніки

Рейтинг ухилення гравця проти конкретного нападника: основа + ранг + Σ внесок техніки + спорядження + знання про нападника. Внесок техніки = `full` (рядок `K.passiveFx`) × `levelScale(дієвий рівень, бойовий рівень нападника)`; дієвий рівень = `рівень навички техніки × Майстерність ÷ K.masteryCap`; `levelScale` = `clamp(дієвий ÷ рівень нападника, K.evaLevel.min, max)` (`numbers.ts`). Частини ухилення (`EvasionPart`) несуть `full`, `skillLevel`, `masteryLevel`, `effectiveLevel`, `ratio` і `levelAdj` (на скільки внесок відрізняється від `full`). `evasionParts(snap, content, attackerLevel?)` без рівня нападника рахує проти нападника рівня навички техніки; `partsAgainst` і `shiftAgainst` перераховують частини проти ворога; `evasionAgainst` додає зсув до рейтингу гравця (бойовий рівень ворога лежить у `data['combat.level']`), а вигляд бою (`fightStatus().player.evasion.parts`) показує частини проти першого живого ворога. Ворожі рейтинги не змінюються.
