# Shinobi Idle

Idle/incremental RPG у дусі Melvor Idle в канонічному світі «Наруто». Веб-застосунок (PWA), TypeScript, Svelte 5. Зараз робиться MVP: зріз від учня Академії до жилета Чуніна.

## Документи

Якщо документи розходяться, діє той, що вище в списку.

1. `docs/Shinobi Idle — MVP — правки зрізу.md` — усі правки складу зрізу.
2. `docs/Shinobi Idle — сюжет усієї гри.md` — сюжет, епохи, правки сюжету MVP.
3. `docs/Shinobi Idle — модель балансу.md` і `docs/Shinobi Idle — MVP — зріз і баланс/` — числа, формули, дані зрізу (`slice.json`, `balance.json`).
4. `docs/Shinobi Idle — інтерфейс і візуальний стиль.md` — вигляд і UX.
5. `docs/Shinobi Idle — MVP — аналіз і план реалізації.md` — етапи 0–9.
6. `docs/Shinobi Idle — MVP — перший закінчений зріз.md`, `docs/Shinobi Idle — гейм-дизайн концепт v3.md` — вихідний задум.

Технічний контракт для коду — `docs/dev/architecture.md`; його читає кожен виконавець і рев'ювер.

## Мова

- Документи, тексти гри, спілкування з автором — українською.
- Код, коментарі, назви гілок, коміти, PR — англійською.

## Архітектура

1. `packages/core` не знає про браузер і UI: без `Date`, `Math.random`, `window`, `document`. Час і RNG приходять ззовні.
2. Увесь контент — дані з ідентифікаторами `core:…`, що проходять схеми Zod. У ядрі немає назв технік чи ворогів.
3. Рядки інтерфейсу й контенту — лише ключі локалізації.
4. UI надсилає ядру команди й читає знімок стану; сам стан не змінює.
5. Гра, офлайн, аналіз бою й боти викликають одну функцію `advance(state, ms)`.

## Git

| Гілка | Призначення |
| --- | --- |
| `main` | Завжди робоча версія. Зливається лише з `test` і лише після згоди автора |
| `test` | Набір фіч, зібраний для перевірки. Зливається з `dev` наприкінці етапу |
| `dev` | Основна робоча гілка. Усі фічі приходять сюди через PR |
| `feat/…`, `fix/…`, `docs/…`, `chore/…` | Одна задача — одна гілка від `dev` |

- Прямих комітів у `main`, `test`, `dev` немає. Виняток — початковий коміт репозиторію.
- PR у `dev` зливається squash-комітом після перевірки й рев'ю. Гілка задачі після злиття видаляється.
- Без `--force` у спільних гілках, без `--no-verify`.
- Коміти — Conventional Commits. Наприкінці повідомлення: `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>`. Опис PR закінчується рядком `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.

## Ролі

Автор дозволив запускати субагентів на розсуд оркестратора.

| Роль | Хто | Модель | Що робить |
| --- | --- | --- | --- |
| Оркестратор | Головна сесія | — | Планує, пише картки задач, приймає рішення, зливає PR, звітує авторові |
| Виконавець | Субагент | sonnet | Робить одну картку у власній гілці, відкриває PR у `dev` |
| Перевіряльник | Субагент із чистим контекстом | sonnet; haiku для механічних перевірок | Перевіряє вимоги приймання з картки: запускає команди, читає диф, відкриває застосунок |
| Рев'ювер | Субагент із чистим контекстом | sonnet; opus для ядра, бою, збережень | Отримує лише номер PR. Читає диф і цей файл, шукає помилки, пише рев'ю в PR |

- Перевіряльник і рев'ювер не отримують історії розмови, пояснень виконавця чи очікуваного висновку.
- Паралельні виконавці працюють у власних worktree й ніколи не правлять ті самі файли.
- GitHub не дає схвалити власний PR, тож рев'ювер лишає коментар-рев'ю з вердиктом `APPROVE` або `REQUEST_CHANGES`.
- Оркестратор сам робить те, що дешевше зробити, ніж пояснити, і все, де потрібне судження щодо дизайну.
- Для простої задачі перевіряльник і рев'ювер — один субагент. PR лише з документами, які написав оркестратор, зливаються без субагента.

## Картка задачі

Кожна задача, яку отримує виконавець, має:

```
ID і назва
Мета: одне речення — що стане можливим
Контекст: документи й файли, які треба прочитати
Зробити: перелік змін
Не чіпати: файли й рішення поза задачею
Вимоги приймання: перевірювані твердження
Перевірка: команди й дії, якими це перевіряється
Ліміт виправлень: 1, 2 або 3
```

Вимога приймання — це те, що можна перевірити командою, тестом або дією в застосунку. «Працює коректно» — не вимога.

## Цикл задачі

1. Оркестратор пише картку.
2. Виконавець робить задачу й відкриває PR.
3. Перевіряльник перевіряє вимоги приймання; рев'ювер читає диф. Обидва позначають кожне зауваження: **блокер**, **важливе** або **дрібниця**.
4. Блокери й важливе повертаються виконавцеві одним списком — це одна ітерація виправлень. Дрібниці виправляються лише якщо це дешево; решта записується в issue.
5. Коли блокерів і важливого немає, а CI зелений, оркестратор зливає PR.

### Ліміт виправлень

| Задача | Ітерацій |
| --- | --- |
| Проста: документи, конфігурація, дані контенту | 1 |
| Звичайна: фіча, екран, модуль | 2 |
| Складна: ядро, бій, збереження й міграції, баланс | 3 |

Коли ліміт вичерпано, виправлення припиняються. Оркестратор сам читає диф, запускає перевірки й вирішує одне з трьох:

- **прийняти** — якість достатня; залишки записати в issue;
- **переробити** — закрити PR і видати нову картку з урахуванням причин провалу; переробка можлива один раз;
- **зупинити** — якщо й переробка не пройшла: задачу відкласти, записати причину в журнал запуску, взятися за незалежні задачі.

## Готово означає

- `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` проходять локально, CI на PR зелений;
- зміни в UI перевірено в браузері на ширинах 375 і 1440 px;
- нові правила й формули покриті тестами;
- у звіті прямо сказано, що не перевірено.

## Автономний запуск

Автор може запустити етап і піти. Тоді:

- питань авторові не ставити; рішення ухвалювати за документами, а де вони мовчать — самостійно, із записом у журнал;
- якщо задача заблокована — перейти до незалежних; зупинитися, коли етап готовий або лишилися тільки заблоковані задачі;
- без згоди автора не робити: злиття в `main`, зміну видимості чи налаштувань репозиторію, платні сервіси, розгортання, видалення чужих гілок, будь-що поза папкою проєкту;
- наприкінці записати журнал запуску `docs/журнал/РРРР-ММ-ДД.md`: що зроблено, PR, ухвалені рішення, що відкладено й чому, що не перевірено, що має вирішити автор.

## Дискусія з автором

Не погоджуватися автоматично. Якщо є суттєві аргументи — заперечити й запропонувати своє. По одному питанню не більше трьох обмінів аргументами в кожен бік; далі діє версія автора. Якщо автор каже, що рішення принципове, — не сперечатися. Якщо позиція автора сильніша — визнати одразу.
